A design brief for the next layer of the platform

Agentic
Recipe Engineering

How an agent can understand, operate, and improve an internal model-optimization library without turning every bad recipe into a multi-hour experiment.

Scope: 4B decoder-only LLM · Chip A · INT8 · trusted internal users · offline / private-network runtime
01 — The thesis

The recipe is not the hard part.

The current recipe shape already captures the model, library version, target chip, stages, dependencies, and quality gate. The hard problem is that an agent can still generate a recipe that is syntactically valid, locally plausible, and expensive to discover as wrong.

The goal is not a better YAML writer. It is an agentic decision system that forms, tests, and revises engineering judgments from evidence.
Agentic layerDecision flowFeedback loop
02 — The expensive failure

A successful run can still be a failed onboarding.

Malformed configuration is visible and relatively cheap to reject. The more important failure is a completed quantization run followed by a meaningful drop in edge accuracy.

Budget is a constraint, not a retry invitation: a failed recipe must not be submitted unchanged. Every attempt should represent a new hypothesis with a recorded reason.
03 — The agentic loop

Make onboarding a bounded experimental reasoning system.

This should not be a free-form autonomous agent. It should be a fixed control loop with dynamic judgment inside it: the platform owns the boundaries; the agent owns exploration, interpretation, candidate selection, and the next action.

04 — The internal library as an environment

Do not turn internal-lib into one giant text blob. Make it explorable.

OpenHands and SWE-agent are useful here for a specific reason: they treat the codebase as an environment that an agent can explore through tools, probes, and feedback. The agent does not need every source file in context before it can make progress.

What a stage does, consumes, produces, and supports.

Source evidence

Where a parameter is interpreted, who calls it, and which tests matter.

Case evidence

Why similar models and targets succeeded or failed, and what engineers changed.

05 — The tool interface

Tool design determines whether the agent reasons like an engineer.

inspect_library_context

Return the selected library version, stages, entry points, environment facts, and knowledge gaps.

inspect_stage

Return stage inputs/outputs, parameters, version differences, callers, tests, and failure patterns.

inspect_model

Extract structure, operators, shapes, parameter scale, and target-chip risk signals.

search_similar_trajectories

Search complete decision histories, not only successful recipes.

explain_source_symbol

Return a bounded source slice, related symbols, tests, and version constraints.

preflight_recipe

Run lightweight probes in the real library environment and separate known, unknown, and unproven.

diagnose_run

Combine logs, stage state, quantization evidence, and edge metrics into the next action.

diagnose_run(run_id="run-042") → category: QUALITY_FAILURE → likely_stage: quantization → evidence: ["attention output error increased"] → allowed_mutations: ["exclude_modules", "approved_clip_parameter"] → forbidden_mutations: ["model.revision", "quality_gate"] → remaining_budget: 2
06 — Diagnosis and memory

A diagnosis should produce an action, not just an explanation.

The agent should not learn that “batch size is usually eight.” It should learn that, for this model, chip, library version, and calibration set, eight produced a particular symptom; an engineer changed it to four for a particular reason; and the edge result moved in a particular direction.

Human correction is not a note attached to failure. It is high-value supervision for future diagnosis, retrieval, and candidate generation.

Weeks 1–2: Offline agent benchmark

Evaluate tool choice, version awareness, evidence use, failure localization, and stopping behavior on historical tasks.

Weeks 3–6: Library environment + critic

Implement library exploration, source evidence, trajectory search, and candidate critique without real GPU submissions.

Weeks 7–10: Diagnostician + preflight

Let the agent obtain facts from the real runtime, expose uncertainty, and generate bounded mutations.

Weeks 11–12: Controlled execution

Allow only one to three evidence-backed candidates and compare invalid runs, first-pass success, edge-quality pass rate, and engineer time.

Closing position: We should not treat the agent as a recipe text generator. We should place it inside an explorable internal-library environment, let it form candidates from source, trajectories, and runtime feedback, and use fixed boundaries to control expensive GPU experiments.
