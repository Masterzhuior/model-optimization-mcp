00
执行决策

先证明瓶颈，再选拓扑。

评估单位是一次真实 onboarding 任务，不是聊天记录。要回答的是：哪个改变能稳定提升首次验证成功率，机制是什么。

01 四类搜索空间02 L0–L4 拓扑03 Owner + scouts04 T09 / T1005 MAST + Who&When06 pass^k + 成本07 screening vs confirmation08 动作空间 schema09 可演化 vs 冻结10 阶段门禁
目标

提升首次验证成功率

Recipe 能执行、能上设备、能满足质量 gate——不靠隐藏修复、重试或 best-of-n。

两张榜

工程可靠性 ≠ 优化质量

A. 能不能发现、组 Recipe、过预检、执行、上设备？B. 在合法候选里，哪个 Pareto 权衡更好？

暂不做

Agent 框架、共享记忆、新 MCP 层

在基线证明需要之前，这些都是混杂变量。

v1.2 变化：实验因子不再是“更多 Agent”，而是 搜索空间 × 拓扑 × 知识干预。一次只改一个。
Gate证明什么典型失败
G1 Recipe 有效Schema + 必填字段结构化输出失败
G2 预检跨字段、能力、兼容性领域约束失败
G3 执行run(config) 完成并有产物实现/环境失败
G4 设备目标设备可加载/运行部署/runtime 失败
G5 质量精度、延迟、内存、热优化质量失败
01
问题重构

“哪个 Agent 赢了”不是好问题。

单次赢家可能只是抽样运气；重复出现的失败模式才是可行动的工程证据。

假设表现先试什么
H1 Skill 歧义必选约束和建议混在一起，触发条件不清GEPA / Skill patch
H2 能力不透明函数存在，但签名、默认值、前置条件、失败语义藏在实现里Repo map / 契约
H3 验证缺口错误配置到昂贵执行才暴露Preflight
H4 编排噪声Skill 输出不一致、工具太多、证据冲突Owner 决策 / 减少角色
H5 成功定义混乱生成 JSON ≠ 执行 ≠ 设备通过 ≠ 质量达标Gate 序列
H6 优化波动校准、设备、runtime、种子、硬件竞争固定协议 / 重复测量
H7 搜索空间错配团队在优化 prompt，瓶颈却在工作流或参数四类空间路由
不要边测边修。 第一轮保留现有实现，只加观测与隔离，其他都不改。
02
被测系统

评估完整链路，但标清每个边界。

Agent 的自然语言只是中间产物；经过验证的结果才是单位。

01 / 请求模型、目标、质量约束、校准数据。
02 / 证据Skills、repo、dataset、device profile。
03 / Recipe基于证据和受支持选项生成完整 JSON。
04 / 预检Schema、能力、兼容性、资源。
05 / 执行run(config)、日志、产物、失败分类。
06 / 设备runtime、精度、延迟、内存、功耗。
07 / 注册版本、审批、lineage。
每一阶段输出带时间戳的机器可读事件。
边界Agent 负责确定性系统负责证据
证据 → Recipe整合、选受支持选项、解释权衡暴露版本/约束；校验必填项证据 ID、选择/拒绝理由、provenance
Recipe → 预检只在诊断可行动时修复Schema、能力查询、兼容性、dry-run错误/警告、耗时、修复次数
预检 → 执行调用受支持入口隔离 workspace、锁依赖、资源限制命令/API、退出码、stdout/stderr、产物 hash
执行 → 设备解读指标；决定一次受控调整冻结 evaluator、固定目标协议质量、延迟、内存、兼容性
设备 → 注册总结适用条件与限制只晋级已批准产物Recipe 版本、commit、数据版本、审批
真实系统原则：Arena 需要真实 run(config)、真实资产、真实设备/KPI oracle。模拟只能验证 harness，不能验证假设。
03
四类搜索空间

优化正确的对象，而不是最显眼的那个。

“优化 onboarding”可能指四件不同的事。混在一个 loop 里，实验就无法解释。

空间优化什么优化器产物评估
S1 解空间bits、group size、校准、混合精度、exclusions、backendAIDE / AgentHPO / Optunarecipe.json 候选质量/延迟/内存 Pareto
S2 工作流stage、工具、顺序、分支AFlow（MCTS）workflow JSONGate 序列 + 成本
S3 指令触发条件、步骤、证据要求、停止条件GEPA / ACESKILL.md / playbook 版本成功率 + 成本 + groundedness
S4 实现runner、adapter、诊断、缓存DGM / AlphaEvolvecode patch全量回归 + 沙箱
顺序

从便宜到昂贵

S3 指令 → S2 工作流 → S1 参数 → S4 实现。从失败所在处开始，不从最时髦的工具开始。

规则

一次只动一个空间

不要在同一轮改 Skill 和工作流。契约和评估器不在任何搜索空间里。

04
L0–L4 拓扑

多 Agent 是拓扑选择，不是目标。

独立重复、角色团队、流水线、种群回答的是不同问题。不要把它们都叫“多 Agent”。

层级是什么回答什么指标主要风险
L0单 Agent任务本身难不难？首次成功率能力上限
L1同配置独立 replicas方差多大？pass@k / pass^k不是协作
L2Owner + scouts + critic + diagnosticians分工是否降低失败？成功率、协调失败handoff 丢信息
L3流水线多 Agent专业化/并行是否值得？Gate 转化、wall-clockcontext 分裂
L4种群 / 演化哪种配置/工作流/技能更好？效应 + 成本过拟合、评估器被利用
onboarding 推荐

一条决策脊柱，外围并行

用 L2：单 owner 持有 task/recipe 状态；scouts 并行只读；critic 检查预检；diagnosticians 每人只提一个 mutation。L3 只给接口清晰的阶段。

什么时候不该用

串行、强耦合、没测量

Recipe → compile → device 是串行耦合。协调成本大于收益，或没有可信 evaluator 时，留在 L0/L2。

外部证据：Anthropic 报告多 Agent 在 breadth-first 研究上收益显著，但 token 成本约 15×；Cognition 警告 peer 多 Agent 在 coding/长上下文任务上会碎片化 context。结论是“放对位置”，不是“越多越好”。

06
任务集

少量任务，高诊断价值。

不要一上来堆二十个随意 Prompt。选能区分“发现、验证、执行、质量”失败的任务。

ID原型测什么Oracle
T01已知正确参考复现已验证路径Recipe + 执行 + 设备容差
T02发现已有函数调用库能力而非重写预期 API 家族
T03不支持的配置尽早拒绝并说明依据早停 + 有依据的解释
T04证据缺失/歧义提问或选安全默认阻塞字段识别
T05非直观有效组合映射到真实支持空间Schema + 跨字段约束
T06执行失败恢复一次有证据的修复受控修复，不盲目改参
T07质量约束量化约束下优化质量Pareto
T08未见模型/设备是否泛化held-out 通过
T09profile-guided读 device profile，选动作并复测指标改善，无回归
T10coordination三源证据才能组 Recipe正确 handoff + 首次成功
Discovery

3 个任务

找主要失败模式。5–10 次。

Validation

2 个任务

确认干预。10–20 次或配对设计。

Held-out

2–3 个任务

最后只用一次；不在上面调参。

07
指标与统计

两张榜、五个 Gate、一个总分都不给。

工程可靠性和优化质量分开报；报分布和成本，不只报最好一次。

榜 A

工程可靠性

首次验证成功率；G1–G5 转化；pass@1 / pass@k / pass^k；修复负担。

榜 B

优化质量

质量、延迟、内存、大小；可行 Pareto 前沿；固定设备/runtime 协议。

指标定义为什么重要
首次验证成功率G5，且无人工修复、无第二次 Recipe最接近产品目标
pass@k / pass^kk 次中任意成功 / k 次全成功能力 vs 可靠性
Cost per verified successtoken + GPU-min + wall-clock + 人工时间防止“最终成功”掩盖成本
协调失败handoff、重复工作、冲突、churn让多 Agent 成本可见
Groundedness关键参数有引用证据的比例减少“看起来合理”的错配
泛化held-out 任务通过率防止过拟合样例
Screening

3 × 5

发现粗粒度失败模式；不要用它给干预排名。

Confirmation

2 × 10–20

配对任务、bootstrap 95% CI、mixed-effects。

停止规则

held-out 无提升

或 cost per success 变差。停，不要加 Agent。

分阶段做实验，不要全因子。

先回答“拓扑有没有用”，再回答“哪种知识干预有用”，最后才问“哪个搜索算子有用”。

协作失败（MAST）

specification · misalignment · verification

handoff 丢信息、忽略输入、重复工作、决策冲突、过早结束、验证不完整、绕过评估器。

归因

Who&When + 消融 + replay

预测责任 Agent/step；去掉一个 role/tool；用 oracle 修正失败 step 后 replay。不能只靠 Agent 自述。

输出：{earliest_boundary, mast, responsible_agent_step, evidence, confidence, candidate_intervention}。这是下一个 patch 的输入。

12
安全与计划

本地执行不等于数据只留在本地。

数据边界覆盖代码、prompt、遥测、日志和产物，不只是 CLI 进程。

威胁控制
Agent 读无关文件只读 repo、最小 workspace、路径白名单
CLI 外发上下文内网端点、网络策略、遥测审计
并发覆盖配置每 run 独立目录、无共享写
复用旧产物Artifact hash + run ID
不可信 Skill/repo 内容工具权限、命令白名单、评审
评估器被篡改外部只读 evaluator、版本校验
GPU 竞争导致失真租约、独占、固定协议
日志泄密脱敏、保留期、访问控制
Week 1

冻结 + 基线

固定 commit/Skills/依赖/模型/evaluator；在 T01–T03 跑 L0 + L1；搭好 trace 和 evaluator。

Week 2

拓扑筛选

L0–L3，3 任务 × 5 次；用 MAST 编码协作失败；决定多 Agent 到底有没有用。

Week 3

知识干预

在胜者上逐项加 repo map、contract、preflight；测 gate 转化和修复负担。

Week 4

搜索 + 确认

GEPA / AFlow / MaAS / AIDE 在 held-out 上比较；10–20 次；只晋级可复现收益。

停止规则：held-out 无提升；协调成本 > 收益；cost per success 变差；失败主要来自基础设施/评估噪声。
13
决策门

让证据决定下一笔投资。

证据决策不要做
反复发现不了已有函数Repo map / API 索引 / 契约再加一个通用 Agent
找到函数但组合错误类型化前置条件 + preflight只堆更多示例
Recipe 合法但执行错误难定位诊断 + 失败分类盲目改参数
跑通但质量不达标单独质量搜索（AIDE/AgentHPO）先重写 Skills
Skill-only 在 held-out 上提升晋级 Skill patch + 回归先建 registry
契约+预检有可重复收益投资轻量契约层默认上 MCP
协调失败占主导回到 L0/L2，减少角色继续加 Agent
所有干预都无改善检查模型/runtime/任务/evaluator推导“需要更多 Agent”
最终建议

先做 benchmark，不要先重写平台。

在一个冻结任务上跑 5–10 次独立尝试；分类最早边界；只改一层；在 held-out 上确认；再决定下一笔投资是 Skill、契约、工作流、拓扑还是训练循环。
