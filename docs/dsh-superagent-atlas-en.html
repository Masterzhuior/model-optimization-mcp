①

Control-plane core: one screen, many sessions

The human faces one Agent; internally the system fully separates "routing" from "execution" and holds exclusive write authority.

Core takeaway: decouple "human faces an Agent" from "system runs sessions". Router is the resident global coordinator that routes but never executes; Worker is a context-isolated execution unit that reports only to Router; Engine holds exclusive write authority via single-writer + atomic claim. The human always sees one unified Agent.
②

End-to-end lifecycle: how one message becomes results from N isolated sessions

Human sends one line → Router splits → multiple Workers run in parallel in isolated contexts → Router unifies into one stream back to the panel.

Key point: parallelism comes from "split + isolated context"; consistency comes from "Router single-writer serializes writes". The human needn't know how many sessions run or their order — they only receive one deduplicated, ordered stream.
③

Attention gate: two-layer filter deciding "should I take it, and how"

Layer 1 is a hard gate (policy / authorization), Layer 2 is a soft assessment (model judgment). Subscribed threads take a fast path around the gate, but gain no new authority.

Design point: the gate is "hard" (only allow-list / rules / mandate, blocking every unauthorized action); assessment is "soft" (model judges relevance and approach). Everything defaults to observe — only the Decision is logged, and the human decides to enable auto after review. This cages "proactivity" inside an auditable box, which is why the paper's "proactively propose a bug-fix PR" can only happen in the prototype with written rules + observe by default.
④

Event-sourced task ledger: every task is a replayable, auditable JSONL

A task is not a field in a state machine, but a stream of append-only events. At any moment you can replay to restore state, assign blame, or roll back.

Why events, not state: record "task progress" as an immutable event stream, not an overwritable field. Benefits — replay on failure (which step, who, why), audit (every action has an owner and a basis), rollback (replay to before an event). This is also the extra layer the dsh-super-agent plugin adds over the prototype repo.
⑤

Competitive landscape map: 2026 control-plane / Agent Runtime tools

Two axes: vertical "native control plane vs bolt-on"; horizontal "has single-writer / atomic-claim consensus". Top-right is the right answer for this wave.

Landscape verdict: in 2026 the control-plane idea of "one screen for a fleet of agents" is converging. The interesting part — dsh's Engine single-writer + Assignment atomic claim and Mission Control's SQLite WAL single-writer + atomic UPDATE claim are the same pattern, independently reinvented. "First writer wins, no double-writes" has become baseline consensus for control planes, not anyone's secret sauce.
⑥

Operating-system analogy: translate "multi-agent scheduling" into kernel terms you know

The community's favorite framing — once mapped to OS concepts, many design decisions click instantly.

One-line memory hook: think of dsh as "a kernel written for a team of Agents" — Router is the interrupt controller, Inline&Spill is the cache policy, speculative is branch prediction, Watchdog is the external control loop. This analogy turns "why is it designed this way" from mysticism into common sense.
