The missing piece isn't context—
it's machine-readable capability contracts.

When critical constraints remain buried in Python implementation details, an agent seeing a tool name or skimming fragmented docstrings does not mean it knows how to use it correctly. The recommended direction: retain Skills + MCP within a tightly controlled closed loop, adding a lightweight contract layer and pre-run validation for critical internal capabilities.

Design principle
Shift capabilities from "the model guesses how to use them" to "the system can explain and verify how to use them."

Let the model understand intent and propose composition plans; let code and tests define and enforce verifiable constraints.

Three hypotheses to test
Retrieval aids discovery

Repository maps and API indexes reduce errors where existing implementations are overlooked.

Contracts govern usage

Versions, preconditions, support matrices, and examples reduce "found it, but used it wrong" mistakes.

Preflight catches early errors

Deterministic validation intercepts errors before triggering expensive run(config) invocations.

↳
Do not mistake inference for fact

The premise that "capability contracts improve first-pass generation success rates" is an engineering hypothesis to be verified, not an established conclusion. The latter part of this report specifies controlled experiments and falsification criteria.

Stop errors before reaching the GPU.

Suppose an agent needs to synthesize a quantization recipe. Usable functions already exist in the internal library, but valid parameters, target platforms, and required preconditions are mostly implicit in code. The agent generates a seemingly plausible configuration; without adequate pre-validation, execution runs for minutes or hours before crashing.

  1. Task Input

    Model, target SoC, precision, and operational objectives

  2. Domain Expert Input

    Analytical conclusions and suggestions, not full executable configs

  3. Agent Assembles Parameters

    Fields, combinations, and defaults assembled by guesswork

  4. Expensive Execution Starts

    Insufficient early gating; defects bypass checks

  5. Post-Run Failure

    Wastes GPU compute and engineer debugging time

The issue isn't just "a hallucinated answer."

The system lacks a mechanism to translate implicit constraints into machine-checkable rules prior to execution; a model judging its own JSON as "reasonable" is not a validator.

Delayed failure · Unnecessary GPU waste

Adding More Context

Improves capability discovery by providing repo maps, relevant source slices, and call sites. However, raw source code often still lacks explicit compatibility ranges, mutual exclusivity rules, and prerequisite chains, while adding retrieval noise.

Adding Capability Contracts + Preflight

Explicitly encodes known rules and uses deterministic validation to intercept invalid configurations. It cannot invent unknown rules from thin air; it requires code evidence, regression tests, and domain engineers to curate collaboratively.

Keep every tool in
its zone of competence.

These open-source projects provide building blocks at different layers, not an out-of-the-box system that solves internal library comprehension and recipe synthesis. The recommended approach is to combine established tooling while curating lightweight domain contracts internally.

Aider · Repo Map

aider.chat ↗
Borrow Pattern

Compresses key classes, functions, signatures, and dependencies into a code map, ranking context by task relevance. Solves "the agent doesn't know where capabilities live."

Use forReference design for internal repo indexing and relevant code retrieval; no need to replace the Harness just for Repo Map.

Griffe

mkdocstrings.github.io ↗
Try Out First

Extracts modules, functions, classes, parameters, and docstrings from Python source or runtime objects, serializing them to JSON and tracking API drift.

Use forGenerating API skeletons and signature manifests locally; do not expect it to automatically discover domain semantics.

JSON Schema / Pydantic

json-schema.org ↗
Adopt First

Provides deterministic validation for JSON structure, field types, required items, and enums. On the Python side, Pydantic organizes models and validation logic cleanly.

Use forHard gate for recipe structural validation; cross-field business logic must still be implemented explicitly.

Repomix

repomix.com ↗
Rapid PoC

Packages codebases into context tailored for LLM analysis, including an experimental MCP mode. Processes code locally, but outbound data routing depends on subsequent model calls.

Use forOne-time local repository analysis; filter sensitive files, audit outputs, and route only to approved internal models.

Promptfoo

promptfoo.dev ↗
Evaluate First

Establishes reproducible evaluation testbenches for models or agents, verifying structure, behavior, token cost, latency, and multi-run variance via local CLI and internal model endpoints.

Use forEmpirically benchmarking Baseline vs. Repo Map vs. Contract vs. Combined approaches rather than relying on demo impressions.

MCP

Protocol Spec ↗
Continue Using

Standardizes tool discovery and invocation with primitives like Resources and Prompts. Can transport contract queries, but the protocol itself defines none of your library's domain semantics.

Use forOptional transport and integration boundary; in-process components can be invoked directly as Python functions first.

LangGraph

GitHub ↗
Defer for Later

Built for stateful, long-running, resumable agentic workflows requiring human-in-the-loop. Does not discover internal APIs or generate quantization rules on its own.

Use forEvaluate only if current Harness infrastructure fails to satisfy persistence, checkpointing, or recovery needs.

Agent Skills Standard

agentskills.io ↗
Continue Using

Encapsulates specialized knowledge, workflows, scripts, and references into reusable skills. On 2026-10-22, Anthropic announced its donation to the Agentic AI Foundation.

Use forRetaining domain workflows for expert skills; the contract layer complements skills with machine-checkable facts without replacing them.

Important boundary: The contract layer does not need to become a separate microservice. For a PoC, it can simply be a local Python package with versioned YAML/JSON metadata and a CLI validator; only expose query interfaces via MCP when cross-process or cross-team sharing is required.

Express "how to use"
as machine-actionable contracts.

Static analysis tools tell you that a function exists, its signature, and where it is defined. However, which SoCs or runtimes support it, which fields are mutually exclusive, and under what conditions execution is prohibited still require team curation. Capability contracts unify both layers and bind them strictly to library revisions.

Proposed contract

A contract should answer 6 core questions

Below is an illustrative metadata design—not the actual API of your underlying libraries, nor an implication that these constraints are already implemented.

  • identityCapability ID, contract version, repo commit SHA, owner
  • implementationUnderlying module/symbol, parameter signatures, exact source location
  • applicabilitySupported model families, target SoCs, runtimes, and precision modes
  • preconditionsRequired upstream steps, prerequisite files/datasets, mutual exclusions
  • examplesVerified minimal examples, known failure cases, and counterexamples
  • validationSchema, semantic business rules, dry-run hooks, test references
capability-contract.yamlSample fields · Maps to actual implementation
id: quantization.prepare
contract_version: 0.1.0
implementation:
  repo: internal-quantization-lib
  commit: <git-sha>
  symbol: <module.function>
  source_ref: <file:line>
applicability:
  model_families: [<approved-family>]
  targets: [<validated-target>]
preconditions:
  - <required-prior-step>
constraints:
  - rule_id: R-001
    severity: error
    when: <predicate over config>
    message: <actionable explanation>
examples:
  valid: <approved-example-id>
  invalid: <known-bad-example-id>
validation:
  schema: <schema-ref>
  preflight: <local-command-or-callable>
status: draft | verified | deprecated
Illustrative metadata only. The contract should point to real source / tests and must be pinned to the library revision used for each run.

What machines can extract automatically

Package and module hierarchies, public functions, signatures and types, docstrings, certain default values, test references, and Git revision deltas. Griffe serves as a solid extraction foundation; Aider Repo Map provides the design pattern for relevance-ranked code maps.

AutomatedRebuilt per release

Business facts requiring explicit curation

SoC and model compatibility matrices, parameter interaction rules, risk levels, mandatory prerequisites, and verified positive/negative examples. Domain engineers can maintain these in their own adapter/metadata repository without blocking on upstream library teams.

Human-curatedEvidence-backed

Validate the recipe
before powering on GPUs.

Never let the same agent act as both author and sole validator. Recipes are synthesized by the Orchestrator; the preflight validator is a deterministic tool that returns structured, machine-locatable diagnostics. The Orchestrator can perform bounded self-corrections before re-submitting for preflight.

Structural Validation

JSON parsing, required fields, type conformity, enums, numerical ranges, and key spelling. Enforced deterministically via JSON Schema or Pydantic.

Output: Field-level errors

Semantic Validation

Cross-field constraints, platform support matrices, mandatory prerequisite steps, and mutually exclusive combinations. Must cite validated rules or test references.

Output: Rule ID and explanation

Environment / Dry-Run

Dependency revisions, filesystem paths, file existence, permissions, and target device/toolchain availability. If the library lacks dry-run mode, run a safe thin probe rather than pretending checks succeeded.

Output: Blocked, warning, or executable

Diagnostics must be structured

Return rule_id, JSON Pointers, severity, observed value, expected condition, evidence source, and actionable guidance. Structured feedback enables reliable agent self-correction far better than ambiguous natural-language tracebacks.

Bound the correction loop

Allow a strictly bounded number of attempts (e.g. maximum 2 retries), logging the initial draft, diffs per round, preflight outputs, and final config. When facing unknown rules, contradictory advice, or high-risk parameters, escalate to human engineers instead of looping endlessly.

!
Fail closed on critical unknowns

If a configuration involves unverified high-risk parameter combinations, unknown platform support, or unconfirmed prerequisites, execution must be blocked or routed to human approval. Low-risk warnings can proceed; critical constraints must never rely on model guesswork.

Run small experiments
before scaling up.

Start with a single internal Python repository, a handful of high-frequency quantization/adaptation capabilities, and historical recipes. Generate and validate JSON recipes offline first without running full GPU or device pipelines. Execute only a representative subset to verify correlation between preflight passes and actual runner success.

Experimental Arms

Same model, same evaluation tasks, same token budget; vary only capability context and contract mechanisms.

Recommended Scale

Select 20–30 representative historical tasks; 2 runs per task per arm. This serves as a pragmatic PoC baseline, not a formal claim of statistical significance.

Define success criteria
before scaling adoption.

Treat capability contracts as a strong PoC candidate without assuming guaranteed victory. The thresholds below represent tentative decision gates established before data collection, not immutable industry standards.

Tentative Go Criteria

Combined Arm D achieves at least a 15 percentage-point improvement in first-pass success over Baseline; zero critical false negatives; gains are not driven by runaway retry iterations; contract authoring overhead remains within acceptable team limits.

Tentative No-Go Criteria

If Arm D demonstrates no consistent advantage over B or C, or if improvements remain purely superficial (valid JSON syntax without semantic or execution gains), pause architectural expansion; isolate error sources rather than piling on more skills or search pipelines.

Counter-hypothesis A

Failures stem from missing requirements, not library ignorance

If the intake request omits target runtimes, hardware, or KPI thresholds, no contract can deduce missing facts. Requires intake clarification and requirement completeness gates.

Counter-hypothesis B

Contracts become incomplete or stale

If critical constraints hide inside edge-case branches outside test coverage, contracts may foster false confidence. Must bind contracts to commit hashes, source refs, and tests, re-verifying upon upstream changes.

Counter-hypothesis C

Model reasoning and multi-step planning are the real bottleneck

If capabilities are discovered and contracts are unambiguous, yet the model fails to map expert findings into the right pipeline, optimize orchestration prompts, planning policies, or use deterministic templating.

Counter-hypothesis D

Maintenance cost exceeds engineering return

If contracts only benefit low-frequency APIs, avoid repo-wide coverage. Focus exclusively on high-frequency, high-failure-cost, constraint-heavy capability hubs.

A useful decision rule: Contracts do not replace model reasoning; they compress what the model must guess. If a constraint can be verified deterministically in code, never force the LLM to speculate about it.

Start with a single failure case.

Keep the PoC minimal: one internal repository, one quantization/adaptation scenario, one contract set, one evaluation task suite, and one preflight entry point. Prove measurable value before expanding across broader skills, platforms, and devices.

  1. Days 1–2 / Baseline

    Select Tasks & Collect Failure Samples

    Curate 20–30 tasks from historical recipe records; gather accepted configs, execution logs, and known failure cases. Annotate critical constraints and ground-truth criteria; freeze baseline pipeline versions.

  2. Days 3–5 / Index & Contracts

    Griffe + Repo Map Principles + Curated Metadata

    Scan target repos locally to generate API indexes and code references; curate compatibility matrices, prerequisites, positive/negative examples, and commit pinning for high-risk stages.

  3. Days 6–8 / Integration

    Expose Query & Validation Interfaces

    Implement local Python APIs or CLI tools exposing capability lookup, contract retrieval, example queries, and validate_recipe. Wrap as MCP tools only when multi-process or client isolation demands it.

  4. Days 9–10 / Benchmark

    Execute Arms A / B / C / D

    Record first-pass outputs, validation diagnostics, retry loops, token costs, and runtime execution results. Audit critical false negatives and publish an evidence-backed Go / No-Go decision.

  5. Post-PoC / Scale

    Scale Proven Patterns Only

    Standardize contract templates and version checkers for capability classes with verified ROI, expanding to other internal libraries. The Recipe Register persists contract versions, execution traces, artifact digests, edge KPIs, and sign-offs.

Explicit Non-Goals

Do not rewrite DeepSeek Harness; do not mandate other teams modify their skills; do not upload internal source to public clouds; do not start with full-repo knowledge graphs or multi-agent swarms; do not require full device-farm execution in round one.

Minimal Deliverables

1. Repo API index; 2. Versioned capability contracts; 3. Local Recipe preflight CLI/API; 4. Orchestrator query integration; 5. 20–30 historical regression benchmarks; 6. A/B/C/D benchmark data with Go/No-Go report.
