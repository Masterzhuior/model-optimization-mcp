01 · Executive summary

Separate planning, execution, reuse, and service

External capabilities have incompatible outputs; conversion and device evaluation are long-running; GPUs and devices are shared resources; Recipes are reusable assets; and the DSH plugin is being asked to perform service-layer work. Putting everything in one Skill or plugin creates version coupling, concurrency problems, and poor recovery.

1Orchestrator Skill: plan and generate

Keep DeepSeek Harness as the agent harness. Its Orchestrator invokes quantization-analysis and target-adaptation Skills, gathers their findings, and performs Recipe Generation. This generation step can stay inside the existing Skill; it does not require a new Generator service.

2Workflow control plane: durable source of truth

Run API, state machine, event history, idempotency, timeout/retry, human wait, GPU queue, device leases, and cleanup belong in a server-side control plane. DSH plugin, Web UI, and CLI use the same APIs.

3Capability Catalog: adapt at your boundary

Skills, MCP tools, CLIs, and Python libraries differ in inputs, outputs, permissions, and evidence. Maintain a small Bridge/Capability Envelope in your platform; external Skill teams do not need to rewrite their work in your Recipe schema.

4Evidence and Recipe Register

Each Run records parameters, versions, logs, binaries, and evaluations. Only a target-evaluated, human-accepted candidate becomes a RecipeVersion. Exact matches can be reused; near matches should seed a rerun of affected stages.

Architecture choiceDefine your own RecipeSpec, Run state, evaluation evidence, and Capability Envelope. Treat Harness, Skills, MCP, the Python library, remote GPU nodes, and device farms as contract boundaries. Changing the agent or adopting another team's Skill should not force a control-plane rewrite.

Seven conclusions

  1. Expert Skills are inputs, not Recipe producers. Quantization analysis and target adaptation solve narrow problems. Their notes, reports, logs, or artifacts inform the upper-level Orchestrator; it combines them during Recipe Generation and emits the complete JSON accepted by the pinned library's run(config).
  2. Generation and acceptance are separate. Validate schema, enumerations, ranges, and mutual exclusions deterministically before execution. A separate Evaluator measures fixed datasets and on-device metrics. A human still decides.
  3. Recipes are scoped, versioned assets. Bind each version to chip, firmware, SDK/compiler, quantization/calibration data, preprocessing, evaluation definition, and artifact digests.
  4. Accuracy debugging is bounded search. The agent diagnoses; a search controller proposes limited trials; the evaluator scores them; a human accepts or rejects the candidate.
  5. Identity, DSH sessions, paths, execution isolation, and GPU scheduling are different layers. The center and selected GPU worker must see the same Run inputs via a verified shared mount or artifact staging.
  6. Keep the DSH plugin thin. Put multi-user identity, durable jobs, and resource queues behind platform APIs to reduce coupling to DSH internals.
  7. No reviewed DSH project provides the whole product. Login, tenant isolation, DSH lifecycle, GPU scheduling, device-farm access, edge KPIs/PPL, and Recipe registration remain separate subsystems.

Shared path contract: central service → selected GPU worker

Path visibility is a hard precondition for submitting a Run. This example uses /srv/onboard. The actual path may differ, but the central process, selected worker's Python process, and any container/Pod mount namespace must resolve it to the same backing file system or verified artifact content. Matching path strings alone is not proof.

Directory boundaryKeep immutable inputs under /srv/onboard/models/<sha256>/ and datasets/<sha256>/. Store recipe/config.json, logs, outputs, and evaluation under runs/<tenant_id>/<run_id>/. Mount approved inputs read-only. A worker can write only to the current Run output. Keep a user's DSH HOME/workspace separate from the platform Run tree.

Before invoking the library, the Runner materializes URI/relative references into concrete absolute paths matching the pinned LibraryConfig schema and stores the exact JSON and hash. Keep Recipe logical references stable; record the worker-bound config hash, image, SDK/driver, storage_id, and input digests on each Run. Verify a shared file system from inside the actual process namespace using its export/claim identity and a marker-file SHA-256. With artifact staging, the Node Agent downloads to the same fixed root, verifies digests, and uploads outputs. A PVC mounted in the DSH Pod does not automatically appear in a GPU worker Pod.

04 · Third-party capability contract

Expert Skills provide reference inputs; the upper-level Orchestrator generates the Recipe

Your current division of labor is clear: quantization-analysis and target-adaptation Skills each solve a narrow problem. Their findings inform the upper-level Orchestrator's Recipe Generation step; those Skills do not directly produce a Recipe and do not need to change. Raw output may be prose, reports, logs, parameter notes, or files. The Orchestrator combines these references with approved Recipe history and generates the complete JSON accepted by the pinned Python library's run(config). The platform team owns the thin Recipe contract and adapters; external Skill teams need not adopt your schema.

Expert Skill output

Focused findings, parameter rationale, constraints, evidence, or artifacts. No common schema or Recipe output is required.

Platform reference

Optionally record source, version, target, original result, and artifact references. Preserve raw output as evidence.

Recipe JSON

The upper-level Orchestrator composes inputs and emits the complete pinned library config. Validate against the target matrix and library schema before execution.

Optional Capability Bridge envelope

The Bridge is maintained alongside an upstream Skill. It records calls and artifacts and normalizes only fields the platform needs; it does not force every Skill into one Recipe schema.

Trust and execution permissionsPin and statically inspect sources. Read-only advice can enter agent context; scripts run in isolated workers; model writes, device leases, and Recipe registration require permission, budgets, approval, and audit. A Skill file is not proof that its scripts are safe.

06 · Recipe Register

A shared Recipe is a versioned evidence asset

Keep Run History and approved Recipes separate. An experimental or failed Run remains useful history; only an accepted candidate becomes a RecipeVersion. Do not match using model name and quantization label alone.

Fingerprint dimensionWhy it mattersReuse behavior
Checkpoint, tokenizer, source revisionOne display name can resolve to different weights or vocabularyAny content change invalidates exact reuse
Target chip, board, firmware, SDK/compilerOperator, kernel, and runtime support differRequire explicit compatibility rules
Calibration/evaluation dataset and preprocessingQuality depends on data and preprocessingPin digests and metric definitions
Library config, tools, container versionsDefaults and parameter semantics changeStore exact config JSON and environment
Binary and evaluation evidenceParameters alone do not prove a good modelRegister after device evaluation and human sign-off

Exact match: reuse an approved artifact when all required fingerprints and evaluation requirements match. Near match: fork a seed Recipe, identify affected stages, and rerun them. Never label a seed as an exact pass; explain each invalidation reason.

07 · DeepSeek Harness service deep dive

Keep DSH in the runtime layer; put identity and durable Runs in the platform

Your service shape is a central server handling login, Recipe/Run control, UI, and scheduling, then submitting work to a GPU node pool. The center is not assumed to have a GPU. A DSH option must be judged by session/file visibility, the OS identity running tools, plugin upgrades, and how Run inputs reach a selected worker.

Service design directionDo not make a DSH login plugin the owner of customer tenancy, long jobs, or GPU scheduling. Use an Identity/Tenant Gateway, tenant-scoped APIs, DSH session/runtime, durable Run scheduler, and GPU worker agents. DSH plugins call the platform APIs. No reviewed candidate delivers that complete stack.

Service options: from shared gateway to isolated workspaces

“Can log in” does not mean “tenants are isolated.” A login proxy may expose one DSH profile, process, host identity, file tree, and tool set. Assess authentication, resource ownership, execution identity, persistent state, and GPU Run integration separately.

Decision rules for your deployment

  1. Trusted internal team, native DSH UI required: compare dsh-team-hub, dsh-passwords, and dusbin on the exact DSH build you run. dsh-team-hub documents clearer workspace/RPC/WS ownership; verify SSO, approval/HITL, browser behavior, plugin distribution, and upgrade/rollback. None is an OS-level customer boundary.
  2. Customers or untrusted shell/Skills: isolate by customer with Linux OS accounts, containers, or Pods. Without K8s, Anko is the clearer OS-user reference and vocsong is a service UX PoC subject to license and deployment constraints. With K8s, evaluate a matched GuoMonth platform/runtime/DSH release set; pointer-a remains an architecture reference while its DSH compatibility issue is open.
  3. Your product UI is primary: evaluate BFF + dsh-ag-ui and use DSH as an Agent backend. This avoids proxying the whole DSH Web surface, but does not provide identity policy, shell isolation, durable Runs, or device access automatically.
  4. Need team memory/knowledge: deepDDW is relevant in that role. Do not count memory namespaces as DSH execution isolation.
  5. Every option: keep GPU build/evaluation in a separate durable Run API and satisfy the shared path contract. No DSH workspace/PVC automatically connects a selected GPU node, local device, or device farm.

Why dsh-login's maintenance burden recurs

A shared DSH process requires a Gateway to keep ownership consistent across RPC methods, WebSocket events, sessions, workspaces, terminals, configuration, and UI behavior. New DSH methods must be classified as readable, ownership-guarded, or privileged. A stale allowlist can break UI functions or expose access. Per-user process/container routing reduces cross-user API filtering but moves work into identity mapping, image upgrades, storage, and lifecycle. A BFF + Agent API avoids mirroring the whole DSH Web surface only if your product can own the primary UI.

None solves the whole onboarding platformAuthentication/RBAC, per-user DSH state, GPU queueing, worker storage, local/device-farm access, PPL/KPI evaluation, and Recipe registration remain separate responsibilities. DSH's safety guidance says it is a developer preview and should not be the only boundary for untrusted workloads.

Plugin owns authentication and resource ownershipAuthorization couples to DSH internals; upstream changes cause bypasses or outagesAuthenticate in a Gateway; authorize resource ownership in server APIs
Any Skill can run arbitrary scriptsCustomer model, tokens, network, or host may be exposedPin source digests/images/permissions and isolate by trust level
LLM freely emits final configWrong fields/defaults, invalid ranges, unsupported targetsSchema + deterministic target validation + allowlisted parameter changes
One KPI is treated as “pass”PPL, task quality, latency, TTFT, throughput, memory, or thermal state is missedUse customer-specific metrics; record device state, warm-up, samples, and environment
Recipe matching uses names onlyCheckpoint, tokenizer, calibration data, SDK, or firmware can be mismatchedContent fingerprint + target compatibility + evaluation fingerprint
Center and GPU worker resolve a path to different filesPython config points to missing or stale worker dataStorage identity/canonical-path preflight or digest-verified staging
GPU/device is selected only in UIUsers double-book boards or exceed capacityServer-side leases, quotas, heartbeats, timeout release
Users share DSH workspace and host privilegesTerminal bypasses UI filters and can read shared files/secretsUse per-user/tenant HOME and OS/container isolation for untrusted workloads
Skill calls live only in chat historyDisconnect/restart/context compaction loses progress and resource ownershipPersist Run state/events; treat agent output as decision input
Isolation follows trustTrusted internal users may start with SSO, per-user workspaces, and controlled tools. Customers or untrusted Skills that can run shell need OS/container isolation and restricted network. Both can use the same Run API and Recipe Register; GPU workers receive only an authorized Run manifest and artifacts.
