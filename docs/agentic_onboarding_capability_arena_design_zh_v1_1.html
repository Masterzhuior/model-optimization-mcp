Capability Arena

端侧模型 Onboarding 的 Agent 能力评测与改进实验场

用可复现、可审计的对照实验，检验现有 Skills、Agent 指令、Python 库接口与量化流程究竟哪里有效、哪里失效。让多个独立编码 Agent 在同一份内部代码库上完成真实的模型接入任务，再根据证据决定应该改进什么。

内网优先同一仓库 / 同一 Skills可复现实验源码不出内网

设计主张：不要先建多 Agent 平台。先构建一个能让失败变得可观测的小型实验 Harness，再由证据决定什么值得变成 Skill、能力契约、脚本或流程规则。

00
CAPABILITY ARENA / 00

先证明问题在哪里，再决定如何重构。

当前目标不是在演示中选出“最聪明的 Agent”，而是找出接入失败或效率低下的主要原因：Agent 能力、Skill 质量、仓库知识缺失、API 可发现性、Recipe 约束、执行校验，还是量化策略本身。

推荐做法

先搭建轻量、本地化的 Capability Arena。先运行 5 次独立实验，固定任务、代码版本、Skills、模型与评估协议，使用隔离工作区和结构化轨迹。Codex 或 Claude Code 负责执行任务；薄控制器只负责实验编号、隔离、超时、结果收集和评分。

暂时不要做

不要先发明一套 Agent 平台。基线测量前，不急于引入角色扮演 Agent、共享记忆、自修改 Skills、新 MCP 层或复杂编排图；这些都可能成为混杂变量。

北极星指标

提高新任务首次生成可执行、通过设备验证的 Recipe 的概率；不允许通过隐藏失败、人工补救、多次重试或昂贵全量运行来美化结果。

01
CAPABILITY ARENA / 01

“哪个 Agent 赢了？”不是最重要的问题。

真正有价值的问题是：在受控条件下，哪些改变能稳定改善任务完成率，改善机制又是什么？单次获胜可能只是抽样运气；重复出现的失败模式才是可行动的工程证据。

待验证假设

Skill 指令含糊：必选约束与建议没有区分，触发条件不清。能力不透明：函数存在，但签名、默认值、适用范围、前置条件与失败语义藏在实现中。缺少预检：错误配置经过很长时间才在昂贵执行中暴露。编排噪声：Skill 输出不一致、工具太多，导致证据互相冲突。成功定义混乱：生成 JSON、Python 执行成功、设备运行成功和质量达标并非同一件事。量化波动：校准数据、设备、runtime、种子和硬件竞争都可能影响结果。

实验原则

这些只是假设，不是已证实的发现。第一轮只增加观测与安全隔离，不要边测量边“顺手修好”系统。

02
CAPABILITY ARENA / 02

评估完整流程，但必须标清每个边界。

评估单位是一次真实 Onboarding 任务，从用户请求一直到经过验证的产物。Agent 的自然语言回答只是中间产物。

端到端路径

01 需求：模型、目标设备、质量与性能约束、校准数据。02 专家证据：现有 Skills 给出发现、支持选项和有依据的参数。03 Recipe：Agent 根据证据和库能力生成完整 JSON。04 预检：Schema、能力、兼容性、文件与资源检查。05 执行：Python 库 `run(config)`、日志、产物与失败分类。06 设备评测：runtime 兼容性、Accuracy/PPL、延迟、内存与产物检查。

边界责任

Agent 负责证据整合、选取支持选项、解释权衡；确定性系统负责暴露真实接口与版本、校验必填项、能力查询、兼容性检查、dry-run 和资源限制。每一阶段都输出带时间戳的机器可读事件。

必须记录

证据 ID、所选参数与被拒绝的备选方案、API 调用、校验告警、重试次数、退出码、耗时、stdout/stderr、产物哈希，以及设备侧质量和性能结果。

03
CAPABILITY ARENA / 03

控制变量，否则实验结果没有解释力。

每个实验都应能回答：到底改了什么，其他条件是否保持一致，结果是否可以复现？

实验纪律

01 统一任务定义：使用规范化任务说明；若要比较不同 Prompt 策略，必须将 Prompt 作为独立变量。02 隔离上下文和文件系统：每次运行使用干净 worktree、独立输出目录与独立会话，提交前不能访问其他 Agent 的结果。03 冻结基线：记录 Git commit、Skills 哈希、配置版本、CLI/模型端点、依赖锁文件、设备/runtime、数据集和评估器哈希。04 记录动作而非隐藏思维链：收集工具调用、读取文件、选用函数、参数、校验消息、重试、耗时与产物；要求简短的证据化决策记录即可。05 区分复现与多样性：同模型同 Prompt 的五次运行衡量抽样波动，不等于五种策略。06 优先配对比较：干预前后复用同一任务、输入、评估协议与硬件等级。07 评估器独立：尽量由 Agent 之外的代码执行验收，避免候选自己给自己打分。

关键禁区

不要让所有 Agent 同时修改共享 Skills 目录。每个改进都应形成独立补丁/分支，单独评测并审核，否则无法判断到底是哪一项改动带来了收益。

04
CAPABILITY ARENA / 04

用少量任务覆盖真实失败模式。

不要一开始就堆二十个随意 Prompt。先选择诊断价值高的代表任务，等基线暴露缺口后再扩充。

建议任务集

T01 已知正确的参考接入：能否用现有 Skills 和库复现已验证路径？验收：Recipe 有效、执行成功、产物与设备检查在容差内。T02 发现已有函数：是否调用库中能力，而不是重复实现？验收：调用预期 API 家族，不出现禁止的重复实现。T03 不支持的配置：能否识别模型/设备/量化组合不可能或不受支持？验收：尽早拒绝并说明依据，不启动长耗时执行。T04 证据缺失或歧义：能否提出必要问题或采用有文档依据的安全默认值？验收：正确指出阻塞字段，不虚构 API 或默认值。T05 不直观但有效的参数组合：能否将专家证据映射到库真实支持的参数空间？验收：Schema 与跨字段约束均通过，执行成功。T06 执行失败与恢复：能否根据日志分类并进行最小修复？验收：最多进行有依据的受控修复，不盲目反复改参数。T07 质量约束下的量化：能否在模型大小、延迟、内存约束下寻找更好的质量结果？验收：固定评测协议下的 Pareto 结果。T08 未见过的模型或目标：检验方案是否能泛化，而非记住参考样例。

对照条件

基线原样运行；仓库地图/API 索引；明确前置条件与支持组合；优化 Skill 操作步骤但不改变底层事实；增加廉价预检；最后才测试多变量/演化方案。一次只改变一个因素。

05
CAPABILITY ARENA / 05

让 Harness 保持轻量，让证据足够丰富。

Codex 或 Claude Code 可以作为执行 Worker。薄的本地控制器负责实验配置、隔离、超时、收集和评分，不要复制 Agent 自己的规划逻辑。

最小组件

实验清单：任务 ID、基线哈希、实验组、预算、设备、评估器。Runner：创建隔离工作区、调用 Agent CLI、施加超时与资源限制。事件记录：统一记录文件访问、工具调用、验证和执行事件。评估器：在 Agent 之外检查 Recipe、执行、产物和设备结果。归档：保存报告、日志、产物哈希、版本与决策记录。

建议目录

`tasks/` 存任务与验收条件；`skills_snapshot/` 保存版本快照；`contracts/` 存能力元数据；`runner/` 存本地执行脚本；`evaluators/` 存独立评估器；`runs//` 存各次运行产物；`reports/` 存排行榜、失败分析和决策记录。

06
CAPABILITY ARENA / 06

从冻结基线到工程决策的一套标准流程。

第一阶段先把现状测清楚；之后按证据选择最小干预，并在同一任务与评估协议下重跑。

阶段 0｜准备

固定代码 commit、Skills、依赖、Agent runtime、模型端点与评估协议。选一个有明确验收标准、耗时可控的参考任务。确认 CLI 的模型流量符合内网数据政策，设置时间、Token、GPU、磁盘预算和终止开关。

阶段 1｜基线

运行 5 次相互独立的尝试，不共享对方结果，不自动修改 Skills。保存最终 Recipe、工具轨迹、执行结果、评估结果，以及带证据引用的简短决策记录。

阶段 2｜诊断

按最早发生问题的边界分类：任务理解 → 证据检索 → API 选择 → Recipe Schema → 预检 → 执行 → 设备/质量。区分 Agent 犯错和系统信息缺失/矛盾，并统计同类失败是否重复出现。

阶段 3｜干预

根据失败类型选择最小改动：改善 Skill 触发条件、建立 API 索引、增加类型化能力契约、添加预检诊断，或改进错误分类。一次只改一层；至少用一个留出任务检查是否过拟合。

阶段 4｜晋级

只有在指标改善且没有不可接受回归时，才把改动升级为长期资产。稳定规则应优先写进可执行校验，而非只靠自然语言提醒。将任务加入回归集。

07
CAPABILITY ARENA / 07

不要用一个神奇总分掩盖不同问题。

至少维护两张排行榜：工程可靠性与量化优化质量。它们的目标、成本和验收方法不同。

A｜工程可靠性

首次 Recipe 有效率；首次预检通过率；API 发现正确率；执行成功率；设备验证通过率；平均重试次数；人工介入次数；完成时间、Token/GPU 成本。每项明确分母与失败定义。

B｜量化优化质量

Accuracy/PPL 或任务相关质量指标；延迟；峰值内存；模型/产物大小；目标设备兼容性。只在固定设备、runtime、校准数据和测量协议下比较。

汇总建议

优先报告通过率、分布、置信区间或重复运行范围，而不是只报告最佳一次。不要把“成功执行”与“质量更好”合并为一个分数；如果业务确实需要总分，必须公开权重和硬性门槛。

08
CAPABILITY ARENA / 08

让 Agent 提出改进，让实验决定哪些改动留下。

只有在基线评测可靠之后，才引入受控的 Agent 自我改进。改进不是让所有 Agent 随意修改系统，而是提出带假设、可回滚、可验证的补丁。

可尝试的改动类型

Skill 描述与触发条件；内部 API 地图/索引；能力契约与参数支持矩阵；Recipe Schema 与跨字段校验；预检与错误诊断；任务澄清策略；量化搜索策略。

演化政策

每个补丁必须关联具体失败事件或缺失要求；写明假设和预期指标；在固定回归集与至少一个留出任务上测试；禁止修改评估器、验收标准和基线证据；保留版本、结果、回滚方法。只对目标任务有效且造成其他任务回归的改动，不应无条件推广为全局 Skill。

09
CAPABILITY ARENA / 09

借鉴 RSIHub 的实验纪律，不必直接搬入整套框架。

RSIHub（《A Composable Framework for Agent-Evolution Methods》）更重要的价值不是“多 Agent 赛跑”，而是为 Agent 演化提供标准生命周期、受保护的评估器、可修改范围、候选历史/来源追踪、恢复与晋级机制。论文的结果是特定基准与运行条件下的证据，不是你们项目的性能预测。

RSIHub 的实验循环

选择候选 → Rollout 执行 → 分析 → 生成变更 → Guardrail 检查 → 独立评估 → 吸收/晋级。实验 Recipe 应记录操作者、基线、允许修改的文件范围、目标任务、评估器、预算和数据划分。

论文结果如何解读

论文报告不同演化方法在不同任务和种子 Agent 上表现不一。部分基准提升明显，另一些提升较小；整体分数提升也可能掩盖某个子集回退。作者还测试了执行模式差异与边界故障，但明确承认这些保证仅覆盖测试过的边界和环境，单次运行的提升不足以证明稳定性。

对你的项目的映射

先实现最小子集：实验身份与版本、候选补丁谱系、冻结评估器、修改范围、预检/护栏、留出任务、失败日志与检查点恢复。不要假设 RSIHub 能直接覆盖公司 GPU、设备农场、内部依赖和安全要求；先验证执行器、资源租约和数据路径。

区分两种 Recipe

Onboarding Recipe：交给 Python `run(config)` 执行的生产配置，描述量化/适配步骤与参数。Experiment Recipe：描述一次实验如何运行，包括 Agent/模型、Skills 版本、任务、评估器、允许改动、预算、随机性和结果。不要把二者混为一谈。

推荐采用顺序

先建立基线与可信评估器；再做单因素干预；只有当结果稳定、版本与修改边界可审计后，才考虑自动化演化框架。

10
CAPABILITY ARENA / 10

“Agent 能跑通”不等于“Agent 找到了更好的模型”。

必须把流程工程能力与量化策略优化拆开评估。前者关注是否选择正确、受支持的流程；后者关注在满足约束时能否找到更优参数。

A｜流程能力

是否选对量化路径；校准资产、目标 runtime、模型结构和 Recipe 字段是否正确；产物能否在目标设备加载。指标包括 API 正确性、Recipe 有效性、执行与设备通过率。

B｜搜索与优化

在流程有效后，是否能在支持范围内选择更好的 bit-width、混合精度分配、校准设置和其他参数。指标包括质量、延迟、内存、产物大小与约束满足情况。

两阶段评估

廉价筛选：Schema、兼容性、校准数据、静态资源估算、小规模代表性评估和提前终止。确认性评估：只运行入围候选，固定设备/runtime、预热方式、重复次数、基准输入、软件硬件版本与产物哈希。

约束与 Pareto 前沿

把质量、延迟、内存、大小视为多目标约束，报告 Pareto 前沿，而不是任意加权后只挑一个分数。先满足硬约束，再讨论权衡。

11
CAPABILITY ARENA / 11

本地执行不等于数据全程只留在本地。

内网限制必须覆盖从读取代码到模型推理、遥测、插件、日志和结果归档的完整数据路径。不能仅凭 CLI 在本地运行就推断源码不会发送到外部服务。

必要控制

只使用公司批准的内网模型服务；确认 CLI 的模型路由、遥测与扩展行为；限制 Agent 工作区和文件权限；每次运行使用隔离目录；禁止访问无关文件和外网；评估器、验收数据与基线不可修改；日志脱敏并设定留存期限；对 GPU/设备使用明确租约和资源配额。

需要纳入威胁模型

Agent 读取超出范围的文件；CLI 将上下文发送到外部端点；并发任务覆盖共享配置；复用旧产物；不可信 Skill/仓库内容诱导越权工具调用；Agent 篡改评估器或阈值；GPU 竞争导致性能结论失真；日志收集不必要的客户信息或机密。

执行前提

Codex、Claude Code 是候选 Worker，不代表自动获得安全批准。必须核验具体企业配置、模型路由、遥测、扩展策略和网络路径；不符合要求时，使用已批准的内网 CLI/模型端点或最小内部封装。

12
CAPABILITY ARENA / 12

两周 PoC：每个阶段都设明确退出条件。

时间安排假设一名工程师可以访问代表性仓库、参考任务、已批准的 Agent runtime 和评估器；需根据 GPU 排队与内部审批调整。

第 1–2 天｜范围冻结

选择 T01 与一个失败诊断任务（T02 或 T03）；固定代码/Skills/依赖版本和验收谓词；确认网络与运行策略；建立隔离工作区、实验清单与评审标准。退出条件：另一位工程师可以复现设置，并理解什么算通过。

第 3–4 天｜最薄 Runner

每个隔离运行启动一个 Agent CLI；收集 Recipe、工具事件、退出码、日志、耗时和产物；实现 Schema 验证、产物存在性与哈希检查。保持为本地脚本，不要先建服务。退出条件：无需手工拼接会话即可重放并评分。

第 5–6 天｜基线复跑

T01 运行五次独立尝试；预算允许时加入 T02/T03。按最早失败边界分类，记录修复成本，并排查硬件、缓存、数据或 runtime 的非确定性。退出条件：能从证据识别重复失败类型。

第 7–9 天｜两项干预

依据实测失败选择最有价值的两项，例如 API 发现、能力契约、Skill 指令或预检；每次只改一个因素，使用同一任务复跑，并加入留出任务。退出条件：能量化是否改善首次成功率。

第 10–12 天｜量化优化（可选）

若流程可靠且资源允许，再单独运行质量优化实验；固定评测协议，记录质量/延迟/内存/大小与设备环境。不要让工程可靠性实验被昂贵的量化搜索拖慢。

第 13–14 天｜决策评审

汇总排行榜、失败分类、成本、回归与安全情况；决定推广某个 Skill、加能力契约、增加预检、改进诊断，或继续收集证据。退出条件：每个后续投资都对应明确证据与可证伪假设。

CAPABILITY ARENA / 13

让实验在 Demo 结束后仍然有价值。

每次运行都应产出结构化、可追溯的资产，而不依赖聊天记录或人工回忆。

应归档的交付物

实验清单与排行榜：任务、实验条件、run ID、版本哈希、各关卡结果、成本、耗时和原始指标。证据轨迹：Recipe、结构化事件、执行日志、校验报告、产物哈希和简短决策记录。失败诊断：最早失败边界、证据、复现次数、估计成本和候选干预。工程补丁：Skill diff、能力元数据、校验器或文档，关联假设与指标变化。优化前沿：可行量化候选的质量、延迟、内存、大小、环境和测量协议。决策记录：变更原因、证据、已知回归、假设、负责人和回滚计划。

建议失败分类

F01 任务理解错误；F02 Skill 路由错误；F03 API 发现失败/重复实现；F04 契约或参数组合不匹配；F05 Recipe 整体组合冲突；F06 执行/runtime 失败；F07 设备部署或加载失败；F08 质量/性能不达标；F09 环境噪声或评估器问题；F10 安全/权限边界违规。每次记录都应定位到最早可证实的因果边界。

反证与应对

若排名随重复运行剧烈变化，说明“赢家”可能只是采样噪声：增加配对重复并优先稳定的确定性约束。若基线任务改善但留出模型/设备退化，说明过拟合：保留留出集，限制单变量变更。若能力契约减少错误却显著增加调用、上下文或延迟，应测量检索精度并采用按任务发现，而不是加载整个目录。若契约与源码签名漂移，应从源码生成签名、版本绑定并加入一致性测试。若 GPU 负载导致延迟排序改变，或校准/评测输入影响质量结果，则固定协议、重复测量并避免超出精度的结论。若所有干预都无改善，先检查模型/runtime 能力、任务歧义、基础设施噪声和评估器质量，不要直接推导出“需要更多 Agent”。

给每个 Worker 同一份实验契约。

以下是受控基线的提示模板。它应保持朴素，不要把答案塞进 Prompt，也不要预设必须采用某种新架构，以免偏置实验。

基线 Worker 指令

你正在执行一次受控的端侧模型 Onboarding 基准任务。请使用当前隔离工作区中的仓库、Skills 与批准工具，严格满足任务验收条件。规则：1）不要假设 API 存在，先检查仓库与可用 Skills。2）优先使用已有且受支持的库能力；无法验证时说明证据缺口，不要编造函数或参数。3）生成要求的 Recipe JSON，所有输出写入指定 run 目录。4）只使用批准工具和配置的内网模型端点，不访问外部服务或无关文件。5）昂贵执行前运行可用的验证/预检；若不存在，记录已检查内容与剩余不确定性。6）不得修改评估器、验收条件、基线源码、共享 Skills 或其他运行的文件。7）失败时根据真实日志分类，只做有证据支持的修改，并记录每次重试与参数变化。8）没有机器可验证证据就不能宣称成功；必须区分 Recipe 生成、Schema 有效、执行成功、设备验证与质量达标。交付：`recipe.json`、简短运行报告（API/函数、证据引用、参数决策、校验、重试和未解决问题）、必要日志及产物哈希。

独立改进提案指令

请根据指定失败事件提出一个最小补丁。输出：失败证据、根因假设、修改文件范围、预期指标变化、潜在回归、回滚方式与验证任务。不要直接改写共享基线；以独立 patch/分支提交。

评审清单

证据是否可追溯？改动是否只针对已观察到的失败？是否改变评估器或验收标准？是否在回归集与留出任务上通过？是否引入额外成本或安全风险？结果是否可复现？

两周之后，团队应该做什么决策？

根据证据选择下一步，不要预先认定某一种技术一定是答案。

决策规则

反复发现不了已有函数：优先做能力发现与机器可读元数据，不要再加一个通用 Agent 来“猜得更好”。找到函数但组合错误：补充类型化前置条件、支持矩阵与预检，不要只堆更多示例。Recipe 有效但执行错误难定位：改进确定性诊断、失败分类和重试边界，不要盲目改参数直到成功。执行成功但质量/性能不达标：单独建立量化搜索实验，不要先重写 Skills。Skill 单独改动就能低成本改善留出任务：晋级 Skill 补丁并加入回归测试。契约 + 预检相对 Skill-only 产生可重复收益：投资轻量能力契约层，集成到现有适配层；不必默认要求 MCP。所有干预都没有改善：检查模型/runtime 上限、任务定义、环境噪声和评估器。

最终建议

先做基准，不要先重写平台。用最小可复现实验场跑出 5 次独立尝试，冻结评估器，记录失败的最早边界。之后按证据逐项验证 Skill、API 索引、能力契约和预检。只有当这些实验能稳定区分好坏改动，再考虑引入自动化 Agent Evolution。

现阶段最值得投资的不是“更多 Agent”，而是更可信的实验基础设施：独立运行、冻结评估、可追溯证据、明确修改边界，以及把重复失败转化为可验证的工程改动。
