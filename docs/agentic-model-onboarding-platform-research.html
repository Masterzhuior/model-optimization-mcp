01 · 结论摘要

四条责任线分别解决“会想、会跑、能复用、可服务”

复杂度来自外部能力没有统一输出、端侧流程长且会失败、GPU/设备要排队、中心服务与 GPU 节点有路径/数据可见性问题、Recipe 是可复用资产、DSH 插件又在承担服务化职责。把这些责任都放在一个 Skill 或插件里，会让版本耦合、并发和审批变得难维护。

1Orchestrator Skill：调度并生成，不当数据库

继续用 DeepSeek Harness 承载上层 Orchestrator Skill：理解任务、调用量化分析/目标适配等专家 Skills、收集参考结果，并在 Recipe Generation 阶段产出配置。这个阶段可以由 Orchestrator 自己完成，不要求另建一个 Generator Skill 或服务。Harness 不持有唯一运行状态，也不独自裁定步骤通过或 Recipe 被接受。

2Workflow Control Plane：长流程只有一个真相源

Run API、状态机、事件历史、幂等键、超时/重试、人工等待、GPU 队列、设备租约和资源释放由服务端掌管。CLI、Web UI、DSH 插件用同一组 API。

3Capability Catalog：技能不改，适配由平台拥有

外部 Skills、MCP 工具、CLI 和 Python 库形态不同。平台用小型 Bridge 统一输入、结果类别、目标硬件、权限和证据要求；提供方无需为你的 Recipe 格式重写 Skill。

4Evidence + Recipe Register：记录为什么可信

每次 Run 留下参数、版本、日志、二进制和评测。只有经目标设备评估和人工最终确认的候选才成为 RecipeVersion。精确命中直接复用；近似匹配作为种子，重跑受影响阶段。

最关键的架构选择第一天定义平台自己的 RecipeSpec、Run 状态、评测证据和 Capability Envelope；把 Harness、Skills、MCP、Python 库、远端 GPU 节点池和设备 Farm 放在契约边缘。更换 Agent 或引入另一个团队 Skill，不应迫使你重写控制面。

七条可直接带走的结论

  1. 专家 Skills 不需要按 Recipe 格式改造。量化分析、目标适配等 Skills 各自解决窄问题，原始结论、报告或产物作为上层 Orchestrator 的参考输入；Orchestrator 在 Recipe Generation 阶段综合并生成经 schema 校验、可交给 Python 库 run(config) 的完整 JSON。
  2. Recipe 生成和验收分开。Orchestrator 生成的 JSON 先经确定性 schema/参数校验，再由独立 Evaluator 用固定数据和端侧指标评估；最终仍需人工确认。
  3. Recipe 是带目标与环境范围的版本资产。绑定芯片、固件、SDK/compiler、量化/校准数据、预处理、评测定义和 artifact digest。
  4. acc-debug 是有预算的候选搜索状态。Agent 诊断，Optuna 生成受限 trial，评测器打分，最终由人工确认。
  5. 账号、DSH 会话、文件路径、执行隔离、GPU 调度是不同层。服务端和节点必须通过共享挂载或 artifact staging 看到同一 Run 输入。
  6. DSH 插件应变薄并调用平台 API。账号、多租户、长任务与设备队列放在 DSH 外，降低插件和 DSH 内部 API/UI 的维护耦合。
  7. 目前没有一个已核实的 DSH 开源项目同时交付生产级登录、租户隔离、可恢复 Agent 会话、中心到多 GPU 节点 Run 和端侧 KPI 闭环。直接服务 API、每人独立 DSH 环境、通用 Workspace 平台各解决一部分；应按你是否要保留原生 DSH Web/终端来选验证路线。

中心控制面 + GPU 节点池

中心服务器持有 Identity、Run API、Recipe/Run metadata、工作流和队列；GPU 节点只执行被授权的 job。按 GPU 型号、SDK/驱动、显存和负载注册能力，再由 scheduler 分配。不要假设中心服务器自己有 GPU。

共享存储先定契约

Python 库若接收文件路径，把同一共享文件系统挂到中心服务器和每个 GPU 节点的相同绝对路径；跨网络/跨机房则按 artifact URI stage 到 worker 上固定的 canonical root。Device Farm 是独立 lease，不等于 GPU worker。

中心服务 → GPU worker 的共享路径契约

把路径可见性定义成提交 Run 前的硬条件。以下用 /srv/onboard 作示例；实际路径可以不同，但必须在中心服务进程、被选中 GPU 节点上的实际 Python 进程，以及相关容器/Pod 的 mount namespace 里完全一致。只检查两台主机的路径字符串相同不够：它们还必须指向同一个文件系统/导出或同一内容 digest。

约定的目录边界/srv/onboard/models/<sha256>/ 与 datasets/<sha256>/ 放不可变输入；runs/<tenant_id>/<run_id>/ 保存当前 Run 的 recipe/config.json、日志、输出与评估结果。Recipe Register 中的已批准模型/数据只读；worker 只能写入当前 run_id 的输出子目录。DSH 用户的 HOME/workspace 和这棵 Run 目录分开授权、分开清理。
预检对象必须一致/通过的条件失败时
中心 Run API / 配置物化进程能读取所引用输入；记录配置的 storage_id、mount_root、artifact URI、相对路径、digest、大小和读写模式拒绝提交或返回输入 artifact 不可用；不生成可运行的 Python config
被选中的 GPU worker 的真实容器/进程同一 storage_id/export/claim；相同的 /srv/onboard 进程内路径；输入可读且只读；当前 Run 输出目录可写返回 STORAGE_PREFLIGHT_FAILED，不调用 Python 库的 run(config)
身份与容量worker UID/GID 或 ACL 与输出目录权限匹配；检查剩余空间、inode、挂载只读/读写模式；拒绝越出当前 Run 根目录的符号链接在调度队列前失败并留下节点/路径/权限证据，不进入长时模型构建

Runner 在调用 Python 库前，按已锁定的 LibraryConfig schema 把 URI/相对路径物化成确定的绝对文件路径，并保存最终传给 run(config) 的 JSON 与 hash。recipe-level 逻辑引用保持稳定；执行记录另存节点绑定后的 config hash、worker image/SDK/驱动、storage_id 和输入 digest。这样同一 Recipe 可以复用，而路径物化或 worker 环境变化仍能审计。

所有节点共挂 NFS/并行文件系统/云文件卷时，需在实际进程命名空间执行读取 marker 文件并比较 SHA-256 的预检，同时核对部署清单里的 export/claim 身份和 POSIX 权限。若用 artifact staging，则由 Node Agent 按同一 manifest 下载到固定的 /srv/onboard 目录、验证 digest，完成后上传输出；节点临时盘的任意路径不得泄漏成 Recipe 的隐式语义。若 GPU worker 是 Pod，必须在 worker Pod 自己声明相同 volume 和 mountPath；只给 DSH Pod 配 PVC 不会自动让 GPU Pod 看见它。

04 · 第三方能力接入

专家 Skills 提供参考输入；上层 Orchestrator 负责 Recipe 生成

你现在的分工是：量化分析、目标适配等专家 Skills 各自解决一个窄问题，它们的结果供上层 Orchestrator 的 Recipe Generation 阶段参考；这些 Skills 本身不直接产出 Recipe，也不需要为此改写。原始结果可以是自然语言建议、日志、报告、参数说明或文件。Recipe Generation 是职责步骤，可以继续由当前 Orchestrator Skill 完成；只有后续维护、校验或团队边界需要时，才考虑拆成独立模块/服务。平台只在有用时保存来源、版本、目标和 artifact 引用，或用薄 Bridge 整理必要信息。Orchestrator 综合多份输入与已批准的历史 Recipe，按目标硬件和 Python 库版本生成该库 run(config) 可接收的完整 JSON。Agent Skills / MCP 解决能力发现和调用形态，不定义你们的参数语义、SoC 支持矩阵、精度门槛或签核条件；这层薄适配与 recipe contract 由平台团队维护。

skill_output

量化分析、适配等专家 Skill 输出各自专项结论、参数依据、限制或证据，供上层 Orchestrator 的 Recipe Generation 阶段参考；这些专家 Skill 本身不直接生成 Recipe，也不要求所有 Skill 采用同一 schema。

platform_reference

平台保留来源、版本、目标、原文/产物引用；需要时抽取少量结论和约束供 Orchestrator 的 Recipe Generation 阶段使用。原始输出仍可作为证据。

recipe_json

由上层 Orchestrator 在 Recipe Generation 阶段汇总参考输入并生成完整配置；经过目标能力矩阵、库版本 schema 与参数约束校验后才能执行。

diagnosis

故障类别、日志证据、原因假设和下一步，可供 acc-debug 或人工判断。

artifact

带 URI、类型、SHA-256、来源 Run、工具版本和可见范围的文件。

evaluation

指标、数值、单位、样本数、数据 hash、设备环境与 gate 结果。

建议状态机

CREATED → PREFLIGHT → PLANNED → QUEUED_GPU → BUILDING → AWAITING_DEVICE → DEPLOYING → EVALUATING → CANDIDATE → HUMAN_REVIEW → REGISTERED

异常状态：NEEDS_INPUT、RETRY_WAIT、DEBUG_PROPOSAL、WAITING_APPROVAL、REJECTED、FAILED_NEEDS_HUMAN、CANCELLED。每次转移记录 actor、前后状态、原因、输入版本和 evidence。

错误分类后再自动化

可安全重试：worker 短暂退出、网络中断、lease 超时，用幂等键避免重复副作用。
需要新提案：精度下降、算子不支持、内存不足。
需要人看：未知错误、目标不支持、同失败签名重复、门槛不清。

不丢状态的长任务

共享 Recipe 是有条件的证据资产

Run History 保存所有尝试；Recipe Register 保存可批准、可复用版本。注册项要指出 model.bin 来自哪次 Run、在哪个目标环境测过、由谁签核。

RecipeVersion 最少字段

  • model source、tokenizer/config 内容 hash 与许可
  • 归一化 RecipeSpec、schema/version、LibraryConfig 转换器
  • Capability Bridge、Skill/CLI/Python runner commit 和镜像 digest
  • 芯片/SoC、hardware revision、OS、firmware、SDK/compiler/runtime
  • 校准/评测集 manifest hash、预处理和 metric 定义
  • model.bin hash/size、日志、性能报告 URI
  • 来源 Run、审批人/时间/结论、支持矩阵和已知限制

Build 与 evaluation fingerprint

对 canonical JSON 计算 fingerprint。排除 Run ID、时间戳、临时路径；保留模型权重、参数、校准集、工具链、目标芯片和软件环境。Evaluator fingerprint 单独计算。

物理 device serial 留在评测证据；复用通常针对 SoC/firmware/runtime 能力类别，不要求同一块板，但需符合设备等价规则。

把 DSH 留在运行时层，账号与工作区属于平台层

为什么 dsh-login 的维护成本会持续存在

这不是单纯因为实现写得不够稳。共享一个 DSH 进程时，插件要跟着 DSH 的 API wire surface 维护每个方法的“普通用户可调用/管理员专用”分类，还要让 session ownership、workspace、WebSocket、终端、配置和前端 UI 的角色门禁一致。当前 README 就记录了一个真实例子：0.3.5 的 allow-list 仍是旧 wire 名称，DSH 0.2.1-rc.2 下普通用户的模型目录、workspace picker 和 provider catalog 会被拒；0.3.6 才从当前 146 个方法 registry 重建分类并加入漂移测试。这个版本有 21 个文件、267 项测试，但双浏览器隔离的真实部署验收仍单独列为待办。 dsh-login 当前 README ↗

架构上的减负方式，是不要在同一个 DSH runtime 里模拟多个 OS 用户：让入口层先验证身份，再把整个浏览器流量路由到该用户/租户自己的 DSH process 或 Pod。这样仍要维护登录、路由、凭据和工作区生命周期，但不必针对每个新增 DSH RPC method 重写跨用户 ownership 过滤。若用 Coder 等通用 workspace 平台，登录、workspace 生命周期和路由可交给它；你的 DSH 插件则专注“选模型/Recipe/设备、提交 Run、展示状态”。

Job manifest 负责把逻辑 artifact 变成 Python 库可用的路径

如果 Orchestrator 在 Recipe Generation 阶段产出的 JSON 必须原样直接交给 Python run(config)，并且 config 包含绝对路径，优先用共享文件系统：中心和 GPU 节点挂同一个 mount_root，路径不必改写。若采用 artifact staging，则先在 worker 下载/校验，再把逻辑 artifact URI 物化成该节点的绝对路径；这个节点绑定后的最终 JSON 才交给 run(config)，并同时保留 canonical Recipe JSON hash 和 execution config hash。不要把中心服务器的 host path 原封不动塞给远端 worker。

{
  "run_id": "run_...",
  "execution_node_profile": "gpu-linux-cuda-...",
  "recipe_json_uri": "artifact://sha256/...",
  "storage": {
    "mode": "shared_posix",
    "mount_root": "/srv/model-onboard",
    "inputs": [{"uri": "artifact://sha256/...", "relative_path": "tenants/.../inputs/model", "sha256": "...", "access": "read_only"}],
    "outputs": [{"relative_path": "tenants/.../runs/run_.../outputs", "access": "run_only_write"]}
  }
}

若改为 artifact_staging，把 mode 改为该模式，节点按 URI 取文件；生成路径字段时使用节点上的 staged absolute path。中心和节点必须报告相同输入 SHA-256，不能只比对路径字符串。

把路径约定落实为 scheduler 的 worker eligibility / preflight gate

你的实际拓扑是中心服务器派单到 GPU 节点池，因此“Recipe 和节点同路径”要在所选的那台节点、实际运行的容器/mount namespace 里证明。中心与每个 worker 先登记同一个 storage_profile_id、共享卷/导出身份、canonical mount root、访问模式和服务 UID/GID/ACL；只比较 /srv/model-onboard 字符串不够。

为什么登录壳会成为维护项目

  • 权限对象持续增加。会话、工作区、文件、WebSocket、终端、插件管理和设备/模型选择有不同调用面；登录成功不代表每个路径都过滤了所有权。
  • DSH 更新造成 wire-surface 漂移。dsh-login README 记录随 DSH 同步 allowlist，并修复创建 workspace 的方法名变化。兼容逻辑应隔离在 DSH adapter，而非散布业务层。
  • 请求身份要传到工具执行。DSH 社区讨论记录 RPC/WebSocket 派发后的 HTTP request context / proxy identity 可能无法到 plugin。身份放在 Gateway 校验，不相信 prompt、URL 或客户端 sessionId；上游需持续核验。
  • 共享 host user 不是强文件隔离。若 DSH terminal 能 shell，同一 Linux user 下 UI workspace filter 保护不了文件和 credentials。
  • 会话队列属于服务层。多用户对同 session 并发 prompt 要串行化；GPU/设备 Run 则有独立作业状态。

90 天推进顺序

A服务与作业契约

定义 Tenant/Workspace/Run/Recipe JSON/CapabilityResult、WorkerProfile、StorageManifest；身份在中心服务验证，DSH 插件只调用 Run API；Run 不依赖浏览器或 DSH session 生命周期。

B中心端到远端 GPU 节点纵切

选一条量化路径和一台 GPU node；做 shared mount 同路径与 artifact staging 两种小测，再跑输入→Orchestrator Recipe JSON→remote run(config)→model.bin→设备→Evaluator→人工签核。

C专家 Skills 与 Recipe Generation 阶段

接入量化分析 Skill、目标适配 Skill 和一个 Python/CLI runner；Orchestrator 调用专家 Skills 并将结果作为参考，在 Recipe Generation 阶段产出库接受的 JSON；记录适配投入、支持面、来源和证据。

D多用户、worker 与资产复用

用 2–3 个用户验证 DSH workspace/凭据/terminal；并发投递多个 GPU job，验证 run path 不串写、worker 崩溃重试、模型 hash 对齐、artifact 隔离，以及 exact hit/seed reuse。

值得先跑的候选

  1. 共享 DSH 插件 A/B：在隔离环境用同一精确 DSH 版本比较 dsh-passwords 与 dusbin/dsh-multi-tenant：登录/SSO、session/workspace ownership、WebSocket、终端/文件/凭据访问、撤权、升级/回滚和备份。前者 GPL-3.0-only 且 Docker 内置 0.2.1-alpha.2；后者 MIT 并支持 OIDC/LDAP；两者都是共享 DSH runtime 的逻辑权限层。
  2. 单机一人一份 DSH：用 Anko 验 OS-user/文件/端口隔离，用 vocsong Portal 验账号开通、每用户容器和自动启停；DSM 作为旧版 PoC 对照。统一量出身份映射、DSH 插件安装、HOME/密钥隔离、资源成本、进程回收、升级回滚、卷备份与恢复；Portal 先解决许可证问题。
  3. Kubernetes 每用户 DSH：先在隔离集群跑 GuoMonth platform + dsh-isolated-runtime 的匹配 release：OIDC、两用户撤权、独立 Pod/PVC、stop/start、插件注入和数据恢复；当前 README 与公开 release 的版本标记不一致，先核对 release manifest。再将 GPU worker 挂入相同存储或验证 artifact staging。pointer-a 留作 NAS/CNFS 和控制面架构参考，先解决 DSH 0.1.2+ 401。
  4. 减少 DSH 专用服务代码：做 Coder 一用户一 workspace/container spike：OIDC/邀请、DSH 私有 App 代理、Key 注入、退出回收、镜像升级。另确认 External Workspace 的许可与 GPU host 纳管限制。
  5. 出站节点：januory gateway / dsh-hub 只评估 node registration、断线重连和控制通道；再验证它们不提供的 job submit、artifact transfer 与 GPU lease 如何实现。
  6. 跨节点路径 preflight：挑中心端与两台不同 GPU node，校验相同 mount root、文件 hash、读写权限；再用 artifact staging 对比冷缓存耗时、重试和回收。
  7. DSH SDK JSON-RPC：做 Runtime Adapter spike，核验恢复、事件、身份映射和并发；Skill/Recipe 流程与 GPU job 不依附于浏览器会话。
我会这样排优先级若是可信内部团队的共享 DSH，先用同一精确版本比较 dsh-passwords 与 dusbin；当前 DSH 0.2.1-rc.1 还需逐个做兼容验证。若要真实客户隔离且已有 K8s，先做 GuoMonth platform + isolated-runtime 的成对 RC 安装 spike，核对版本清单、插件注入、用户撤权和数据恢复；它仍是单节点/单平台副本、可信成员的 alpha/RC。pointer-a 更适合作为 NAS/CNFS 与控制面架构参考，当前公开 issue 暴露旧版兼容阻塞。没有 K8s 时再比较 Coder workspace 与 Anko OS-user。无论选哪种，都没有提供你的中心 Run API、多 GPU worker 调度、GPU 节点共享路径/文件传输、Device Farm lease 和 Recipe Register。
