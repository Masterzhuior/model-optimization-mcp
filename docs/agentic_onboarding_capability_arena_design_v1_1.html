Capability Arena

A controlled, evidence-driven way to discover whether the current Skills, agent instructions, repository interfaces, and quantization workflow are actually good enough — by asking independent coding agents to solve real model-onboarding tasks against the same internal codebase.

Local-firstSame repo / same skillsReproducible runsNo source-code egress

Design thesis: do not build a multi-agent platform first. Build a small experimental harness that makes failure observable, then let evidence determine what deserves to become a Skill, contract, script, or workflow rule.

00
Executive decision

Prove what is broken before redesigning the system.

The immediate objective is not to find the cleverest agent in a demo. It is to locate the dominant causes of failed or inefficient onboarding: agent capability, Skill quality, missing repository knowledge, API discoverability, Recipe contracts, execution validation, or quantization strategy.

Recommendation

Build a thin, local Capability Arena

Start with five independent runs, one frozen task, one frozen codebase/Skills snapshot, isolated workspaces, a deterministic evaluator, and structured traces. Keep Codex or Claude Code as the worker interface; let a small harness manage experiment IDs, files, evaluation and comparison.

Do not do yet

Do not start by inventing an agent framework

Do not add role-playing agents, shared memory, self-modifying Skills, a new MCP layer, or a large orchestration graph before the baseline tells you which failure mode matters. Those may eventually help; at this stage they are confounding variables.

01
Problem reframing

“Which agent wins?” is a weak question.

The useful question is: under controlled conditions, which changes reliably improve task completion, and through what mechanism? A winner can be a lucky sample; a repeatable failure pattern is actionable engineering evidence.

Hypothesis A

Skill ambiguity

Instructions are incomplete, overly broad, badly triggered, or fail to distinguish mandatory constraints from suggestions. Agents improvise incompatible workflows.

Hypothesis B

Capability opacity

Useful Python functions exist, but signatures, supported combinations, defaults, preconditions and failure semantics are hidden in implementation or scattered documentation.

Hypothesis C

Validation gap

The system permits a Recipe to reach expensive execution before cheap checks catch invalid fields, unsupported combinations, missing assets or impossible target constraints.

Hypothesis D

Orchestration noise

Too many loosely specified tools or inconsistent Skill outputs increase context load and make it hard to decide which evidence should control the Recipe.

Hypothesis E

Objective confusion

“Succeeded” may mean JSON was emitted, Python execution completed, the target device ran, or quality/performance met acceptance criteria. These are not equivalent.

Hypothesis F

Optimization variance

Quantization results may vary due to calibration, model/device/runtime versions, seeds, hardware contention or metric noise rather than agent reasoning.

A benchmark should expose the system’s hidden assumptions. It should not merely reward the agent that is best at guessing them.

These are hypotheses, not findings. The first experiment should preserve the current implementation as-is, except for instrumentation and safe isolation. Do not “fix” the system while measuring it.

03
Experimental principles

Control the variables that would otherwise make the result meaningless.

01

Same task specification, not necessarily identical free-form prompt wording

Define one canonical task brief and inject it into each run. If comparing strategy prompts, label that as a separate experimental factor rather than changing instructions invisibly.

02

Independent context and filesystem state

Every run gets a clean worktree or copy, isolated output directory, separate conversation/session, and no access to peer results before submission. Shared read-only inputs are acceptable; shared mutable outputs are not.

03

Freeze the baseline

Record Git commit, Skill hashes, prompt/config version, agent CLI version, model endpoint/version, dependency lockfile, device/runtime, dataset and evaluator hashes. “Same repo” is not enough if the repo changes mid-run.

04

Observe actions, not private chain-of-thought

Capture tool calls, files read, functions selected, parameters, validation messages, retries, time and outputs. Do not depend on collecting hidden reasoning. Ask agents for concise decision records with citations to concrete evidence.

05

Separate reproducibility from diversity

Five runs of the same model and prompt measure sampling variability and robustness. They do not prove five different strategies. Add strategy variants only in a later, explicitly labeled arm.

06

Prefer paired comparisons

For each intervention, reuse the same task, input assets, evaluation protocol and hardware class. When stochasticity is material, repeat runs and report distributions rather than a single “best” score.

07

Never let a candidate grade itself

Acceptance checks should be implemented outside the agent where possible. Human reviewers can adjudicate ambiguous failures, but they should not know which candidate produced a result during initial scoring if feasible.

04
Benchmark design

A compact task suite that tests the real failure modes.

Do not begin with twenty arbitrary prompts. Choose a few tasks with different diagnostic value, then expand only when the first results expose gaps.

Use only models, datasets, devices and tasks approved for internal testing. The expected oracle can be an accepted reference Recipe, a set of valid parameter ranges, or a deterministic pass/fail predicate; it need not be one exact JSON file.

Experimental conditions / change one factor at a time

C0 · Baseline

Current system, unchanged

Current Skills, repository, docs, agent instructions and Python library. Add instrumentation only. This is the anchor for all claims.

C1 · Discovery aid

Repo map / API index

Add a generated, read-only inventory of relevant modules, public functions, signatures, docstrings and tests. Keep Skill text unchanged to isolate retrieval benefit.

C2 · Capability contract

Preconditions and supported combinations

Expose machine-readable capability metadata: inputs, types, constraints, examples, compatibility and known failure modes. Do not change the agent prompt beyond telling it where to query.

C3 · Skill refinement

Better procedure, same underlying facts

Improve trigger, task sequence, evidence requirements and stop conditions. Avoid simultaneously adding new APIs and changing schemas.

C4 · Preflight

Cheap validation before expensive execution

Add schema and compatibility checks plus resource estimates. Measure avoided failures and overhead, not just pass rate.

C5 · Combined

Only after single-factor evidence

Combine improvements that showed independent or complementary value. Test whether interactions create regressions or extra complexity.

Experimental caution: these are proposed arms, not a claim that every intervention is needed. If the first benchmark shows that a simple Skill correction fixes the dominant failure, do not build a contract registry just because it appears architecturally elegant.

06
Run protocol

One disciplined cycle from frozen baseline to decision.

Phase 0
Prepare

Freeze the baseline and choose a safe task

  • Pin code commit, Skills, dependency versions, agent runtime, model endpoint and evaluation protocol.
  • Choose a reference task with a known acceptance oracle and bounded runtime.
  • Verify that the CLI’s model traffic and any extensions comply with the internal-only source-code policy.
  • Set time, token, GPU and disk budgets; define cleanup behavior and a kill switch.
Phase 1
Baseline

Run five independent attempts without peer learning

  • Each worker starts from a clean workspace and the same initial materials.
  • Agents may use the current Skills and allowed internal tools, but cannot read other runs’ output.
  • Capture final Recipe, tool trace, execution outcome, evaluation result and a short decision record with evidence references.
  • Do not permit automatic Skill edits or shared-memory updates during this phase.
Phase 2
Diagnose

Classify failures by the earliest causal boundary

  • Review failures in order: task understanding → evidence retrieval → API choice → Recipe schema → preflight → execution → device/quality.
  • Separate an agent mistake from missing or contradictory system information.
  • Record whether the same failure recurs across independent runs.
  • Use a human reviewer for ambiguous cases, blinded to candidate identity where practical.
Phase 3
Intervene

Change one layer, then replay the same task

  • Choose the smallest intervention that directly addresses a measured failure class.
  • Examples: clearer Skill trigger; API index; typed capability metadata; preflight diagnostic; stronger execution error classification.
  • Version the change and rerun the same task under the same evaluation setup.
  • Use held-out tasks to check that the fix generalizes and has not merely overfit the reference example.
Phase 4
Promote

Turn proven changes into maintained assets

  • Promote a Skill change only if it improves measured outcomes without unacceptable regressions.
  • Promote a capability contract when agents repeatedly need facts that should be machine-checkable and stable.
  • Promote deterministic checks into code rather than relying on prose when a rule can be validated reliably.
  • Update the benchmark itself as a regression suite for future Skills, libraries and model/runtime changes.
07
Metrics and scoring

Use two leaderboards, not one magic score.

A Recipe that executes correctly but produces poor quality is different from a high-quality Recipe that was found through a fragile, expensive process. Keep those dimensions visible.

Scoreboard A

Engineering reliability

Can the agent discover existing capabilities, generate a valid Recipe, pass preflight, execute safely and reach the device-evaluation stage with minimal repair?

Primary outcome: first-attempt verified success rate.

Scoreboard B

Optimization quality

Among technically valid runs, which Recipes satisfy quality and device constraints, and which offer the best trade-offs in quality, latency, memory and model size?

Primary outcome: feasible Pareto frontier, not a single universal winner.

Score aggregation guidance

For the first iteration, prefer a gate sequence over a weighted score: (1) safe/valid Recipe, (2) preflight pass, (3) execution pass, (4) device evaluation pass, (5) quality/performance constraints satisfied. Report conversion rates between gates. Only compare optimization quality among runs that reach comparable evaluation conditions.

Why not one 0–100 score? A weighted average can hide catastrophic failures: excellent latency should not compensate for a broken artifact, and a valid JSON file should not compensate for unacceptable accuracy loss. If a business decision later needs a composite score, publish the raw metrics and weights beside it.

Skill evolution

Let agents propose improvements. Let experiments decide what survives.

Self-improvement is useful only when candidate changes are isolated, reviewed and evaluated against tasks they did not write themselves.

Important anti-pattern: never let all agents edit the same shared Skill directory during a race. That creates contamination, makes attribution impossible, and rewards the agent that happens to write last. Each proposal must be a patch in a branch/worktree, reviewed and replayed separately.

Evolution policy

  • Every proposed change references at least one concrete failure event or missing requirement.
  • Every patch has a named hypothesis and a predicted measurable effect.
  • Every patch is evaluated on a fixed regression subset and at least one held-out task.
  • Changes that only improve the authoring task but regress other tasks are rejected or scoped narrowly.
  • Approved Skill versions and contracts are immutable for the duration of an experiment.
  • All accepted changes retain the baseline comparison and rationale for future rollback.
R
Research note · RSIHub

Borrow the experimental discipline, not necessarily the whole framework.

RSIHub is a composable framework for experimenting with agent-evolution methods. Its relevance here is not “make agents compete”; it is how to keep candidates, evaluators, allowed mutations and evidence under control while testing whether a change genuinely improves outcomes.

What RSIHub contributes

An auditable evolution loop

Select a candidate → run a rollout → analyze evidence → propose a mutation → enforce guardrails → evaluate → archive or promote. The framework separates the candidate being changed from the evaluator that judges it.

What it does not prove

One good run is not a reliable improvement

The paper reports task-dependent results and acknowledges execution-fidelity differences and the need for repeated runs. Aggregate gains can hide regressions on individual splits. Treat the results as evidence that controlled evolution is worth studying, not as a guarantee for your quantization workflow.

Reported benchmark results — context, not a forecast

The paper reports best overall Pass@1 changes for several seed-agent / benchmark combinations. These are results from its own setup, not expected gains for model onboarding.

Keep two recipes distinct

Production artifact

Onboarding Recipe

The JSON configuration that describes the supported quantization/adaptation workflow and is consumed by the internal Python library’s run(config). It must pass schema, semantic preflight, execution and target-device checks.

Experiment artifact

Experiment Recipe

The manifest for one trial: task ID, worker/runtime, repo and Skill versions, allowed mutation surface, evaluator version, resource budget, seed/run index and output locations. It explains how the result was produced, not how to quantize the model.

Recommended adoption order

1

Baseline first

Run five independent workers against the same task, frozen code and Skills, isolated workspaces, and the same evaluator. Do not let workers see each other’s results or edit shared Skills.

2

Controlled interventions second

Change one variable at a time: API index, Skill trigger/instructions, capability contract, or preflight. Replay the same task, then check at least one held-out task.

3

Evolution only after the evaluator is trustworthy

Allow agents to propose patches only after run identity, lineage, evaluator protection, mutation limits and rollback are implemented. Treat automated promotion as a later phase, not a PoC prerequisite.

Decision for this project: implement the smallest RSIHub-inspired subset — immutable experiment manifests, candidate lineage, frozen evaluator, allowed-change boundaries, structured failure records and held-out checks. Do not adopt a full evolution framework until the baseline shows that controlled Skill/contract evolution is the bottleneck and the existing environment can support the extra runtime complexity.

Compatibility checks before adopting the framework

  • Can its execution layer operate within the company-approved network and data boundary?
  • Can it schedule or safely coordinate the actual GPU and target-device/device-farm resources?
  • Can dependencies, model endpoints, device runtimes and evaluation assets be pinned and reproduced?
  • Can it capture traces without leaking source code, customer data, credentials or proprietary artifacts?
  • Does its execution abstraction fit the current Python library and harness, or would an adapter be required?

Quantization quality exploration

Do not confuse “the agent can run it” with “the agent found a better model.”

Once a Recipe is valid and reproducible, a second experimental loop can explore quantization choices. It needs a stricter protocol because quality metrics are costly and can be noisy.

Track A

Workflow competence

Is the right supported quantization path selected? Are calibration assets, target runtime, model architecture and recipe fields correct? Does the result build and load on the target?

API correctnessRecipe validityDevice pass

Track B

Search and optimization

Given a valid workflow, does the agent choose better bit-widths, mixed-precision assignments, calibration settings or other supported parameters under the task’s constraints?

QualityLatencyMemoryArtifact size

Recommended two-stage evaluation

A

Cheap screen

Schema and compatibility checks, calibration-data validation, static resource estimates, small representative evaluation if approved, and early stopping for clearly infeasible candidates.

B

Expensive confirmatory evaluation

Run only shortlisted candidates with pinned device/runtime, warm-up and repetition policy, fixed benchmark inputs, recorded software/hardware versions, and artifact hashes.

Use constraints and a Pareto frontier

For each candidate, record a metric vector rather than immediately compressing everything into one score:

First discard infeasible candidates. Among feasible candidates, retain those that are not dominated across relevant objectives. A candidate is dominated if another is at least as good on all tracked objectives and strictly better on one. Human stakeholders can then choose based on actual deployment priorities.

Safety and validity rule: the Arena should never encourage agents to fabricate calibration results, bypass quality gates, alter evaluator code, or change acceptance thresholds. The evaluator is read-only to the worker; candidate configuration and evaluation results are separate artifacts.
10
Isolation and security

Local execution is not the same as local-only data flow.

The source code and task data must remain within the company-approved environment. This is an architectural invariant, not a note at the bottom of the README.

Required controls

  • Use an approved internal model endpoint or approved local model runtime.
  • Verify all CLI, extension, MCP, telemetry and crash-report paths.
  • Disable unapproved external network access from worker sandboxes.
  • Mount source repositories read-only where practical; write only to a run-specific workspace.
  • Keep credentials out of prompts, traces, manifests and artifacts.
  • Set CPU/GPU/memory/disk/time limits and clean up abandoned processes.
  • Use separate device/resource leases to avoid concurrent-run interference.
  • Keep raw traces and model/data artifacts inside approved storage with access control.

Threats to account for

  • Agent reads unrelated files because its workspace is broader than intended.
  • CLI silently sends telemetry or context to an external endpoint.
  • Parallel agents overwrite shared configs or reuse stale output artifacts.
  • Untrusted Skill text or repository content induces unauthorized tool use.
  • Agent modifies evaluator, test data or acceptance thresholds.
  • GPU contention creates misleading latency/quality measurements.
  • Logs capture secrets, customer identifiers or proprietary data unnecessarily.
Tool choice is conditional: Codex and Claude Code are possible worker runtimes, not pre-approved security decisions. Before use, validate the exact enterprise configuration, model routing, telemetry behavior, extension policy and network path with the company’s security/IT requirements. If any part is not approved, use an approved in-house CLI/model endpoint or a minimal internal wrapper.

Implementation plan

A two-week PoC, with explicit exit criteria.

This timeline assumes one engineer can access a representative repository, a safe reference task, an approved agent runtime and an evaluator. Adjust for GPU queueing and internal approvals.

Days 1–2

Scope and freeze

  • Select T01 and one failure-oriented task (T02 or T03).
  • Pin code/Skills/dependencies and define exact success predicates.
  • Confirm runtime and network policy; establish isolated workspaces.
  • Write a one-page experiment manifest and reviewer rubric.

Exit: another engineer can reproduce the setup and understand what “pass” means.

Days 3–4

Build the thinnest runner

  • Launch one agent CLI per isolated run, with consistent instructions and budget.
  • Collect Recipe, command/tool events, exit codes, logs, timing and artifacts.
  • Implement schema validation and artifact existence/hash checks.
  • Keep the runner as a local script rather than a new orchestration service.

Exit: one complete run can be replayed and scored without manually reconstructing the session.

Days 5–6

Run baseline replicas

  • Run five independent attempts on T01; add T02/T03 if budget allows.
  • Classify each failure at the earliest boundary and record repair burden.
  • Check for non-determinism from hardware, cache, data or runtime.
  • Produce a first leaderboard and failure taxonomy.

Exit: the team can identify the top recurring failure modes from evidence.

Days 7–9

Test the two highest-value interventions

  • Choose interventions based on observed failures, not architectural preference.
  • Examples: better API discovery, a minimal capability contract, clearer Skill instructions, or preflight checks.
  • Change one factor at a time and replay the same tasks.
  • Use at least one held-out task to detect overfitting.

Exit: quantify whether the intervention improved first-attempt success and at what cost.

Days 10–12

Separate quality optimization if feasible

  • Choose one bounded quantization task with known acceptance constraints.
  • Run cheap checks on all candidates; reserve full device evaluation for a shortlist.
  • Pin benchmark and device protocol; record raw metric vectors.
  • Do not mix quality ranking into the engineering-reliability score.

Exit: a reproducible optimization report or a clear reason to defer the expensive track.

Days 13–14

Decision review and next increment

  • Review baseline vs intervention with raw data and uncertainty.
  • Decide what should become a Skill patch, contract, deterministic validator or repository documentation.
  • Promote only approved changes; retain old versions for rollback.
  • Write a short architecture decision record with assumptions and falsification conditions.

Exit: one measured improvement is merged, or the team has evidence that the hypothesis was wrong.

Risks and falsification

Write down what would prove the design wrong.

A serious proposal should contain conditions under which the team should stop investing in it.

Risk: “winner” is mostly random sampling noise
Signal: ranking changes across repetitions; no candidate dominates consistently. Response: increase repeats for a small paired task set, compare distributions and use stable intervention effects rather than crowning a single winner. If variation remains high, prioritize deterministic constraints and evaluation stability.
Risk: benchmark overfits one reference Recipe
Signal: baseline task improves but held-out model/device tasks regress. Response: maintain a held-out set and vary only one dimension at a time. A change that only memorizes one example should not be generalized into a global Skill.
Risk: more metadata makes the agent slower or more confused
Signal: capability contract reduces errors but increases tool calls, context use or latency enough to offset the benefit. Response: measure retrieval precision, size and time; use task-scoped discovery rather than loading the whole contract catalogue.
Risk: a capability contract becomes a second, stale source of truth
Signal: metadata diverges from code signatures or supported combinations. Response: generate signatures from source where possible, version contracts with the repo, run contract/code consistency tests, and clearly label manually maintained business constraints.
Risk: quantization ranking is invalid due to environment noise
Signal: latency rankings shift with GPU load, or quality varies with different calibration/evaluation inputs. Response: pin protocol, separate functional and performance testing, record environment, use repeated measurements and avoid claims beyond measurement precision.
Risk: CLI/runtime is not acceptable for proprietary code
Signal: model requests, telemetry, extensions or tool calls cannot be proven to stay within approved boundaries. Response: stop the experiment using that runtime; switch to a company-approved in-house model endpoint or local wrapper. Do not treat “runs on my laptop” as evidence of data locality.
Falsification conditions for the overall approach:
1) If the current system already has high first-attempt verified success across representative tasks, the Arena may only need to become a regression test, not a platform initiative.
2) If failures are almost entirely caused by nondeterministic infrastructure or unavailable hardware, Skills/contract work will have limited leverage until that infrastructure is stabilized.
3) If single-factor interventions cannot produce a repeatable improvement on held-out tasks, do not promote a complex multi-agent or self-evolving architecture.

Operational prompts

Give every worker the same contract for the experiment.

The prompt below is a starting point for a controlled baseline. Keep it deliberately plain; avoid embedding the “answer” or prescribing a new architecture that would bias the experiment.

Baseline worker instruction

You are executing one controlled model-onboarding benchmark task.

Your goal is to complete the task using the repository, Skills, and tools available in this isolated workspace. Follow the task acceptance criteria exactly.

Rules:
1. Do not assume an API exists. Inspect the repository and available Skills before selecting an implementation path.
2. Prefer existing supported library capabilities over reimplementing equivalent functionality. If you cannot verify a capability, state the evidence gap rather than inventing a function or parameter.
3. Produce the required Recipe JSON and keep all task outputs under the assigned run directory.
4. Use only approved tools and the configured internal model endpoint. Do not access external services or unrelated files.
5. Run available validation/preflight checks before expensive execution. If no such check exists, record what you checked and what remains uncertain.
6. Do not change the benchmark evaluator, acceptance criteria, source baseline, shared Skills, or other runs' files.
7. If execution fails, classify the failure using concrete logs, make only evidence-backed changes, and record every retry and changed parameter.
8. Do not claim success without machine-verifiable evidence. Distinguish Recipe generation, schema validity, execution, device validation, and quality acceptance.

Final deliverables:
- recipe.json
- a concise run report listing API/functions used, evidence references, key parameter decisions, validations, retries, and unresolved risks
- all required execution artifacts and logs
- no modifications outside the assigned workspace unless explicitly permitted by the task manifest.

Independent improvement-proposal instruction

Review the supplied benchmark traces and failure taxonomy. Propose one narrowly scoped change to improve a measured failure mode.

You may propose a Skill patch, repository documentation/API index, machine-readable capability metadata, deterministic preflight check, or diagnostic improvement. Do not modify the baseline directly.

Your proposal must include:
1. Failure event IDs and concrete evidence supporting the hypothesis.
2. The smallest proposed diff and exactly which files it changes.
3. A falsifiable prediction (which metric should improve and why).
4. Possible regressions or added cost.
5. A test plan including at least one held-out task.
6. A rollback criterion.

Do not claim the change works until it has been independently evaluated against the frozen baseline.

Reviewer checklist

  • Does the result satisfy the task’s acceptance criteria, not merely the agent’s own summary?
  • Was an existing capability used where one was available and appropriate?
  • Are critical parameters grounded in source, Skill evidence, contract metadata or a validated reference?
  • Did preflight catch invalid configurations before expensive execution?
  • Are all retries, parameter edits and human interventions recorded?
  • Are model quality and performance metrics produced by the frozen evaluator?
  • Did the run stay within the approved data and tool boundary?

Final recommendation

Start with a benchmark, not a platform rewrite.

Build the smallest reproducible harness that can run five independent agents against one frozen real onboarding task. Collect the Recipe, tool/API events, execution evidence and device metrics. Use the resulting failure clusters to select the next intervention. Keep engineering reliability and quantization quality separate. Promote only changes that beat the baseline on held-out tasks.
