缺的不是上下文，
而是机器可读的能力契约。

当关键约束藏在 Python 实现里，Agent 看到了一个工具名、读到零散文档，并不等于知道怎么正确使用它。推荐方向是：保留 Skills + MCP，把它们放进一个更可控的闭环；为关键内部能力增加轻量契约层和运行前预检。

Design principle / 设计原则
把能力从“模型猜怎么用”，变成“系统能说明、能验证怎么用”。

让模型负责理解需求、提出组合方案；让代码和测试负责描述并执行可验证的约束。

Three claims to test / 三个待验证主张
检索帮助发现

仓库地图与 API 索引能减少“没找到已有实现”的错误。

契约约束使用

版本、前置条件、支持矩阵与示例能减少“找到却用错”的情况。

预检提前拦截

确定性校验能在调用昂贵的 run(config) 前暴露一部分错误。

不要把推断写成事实

目前“能力契约会提高首次生成成功率”是值得检验的工程假设，不是已证明结论。本文后半部分给出对照实验与反证条件。

把错误拦在 GPU 之前。

假设 Agent 需要生成一份量化 Recipe。内部库已有可用函数，但合法参数、适用平台和必要前置条件主要隐含在实现里。Agent 生成了看似合理的配置，前置检查不足，执行一段时间后才报错。

  1. 任务输入

    模型、目标芯片、精度与运行目标

  2. 专家参考

    分析结论与建议，不是完整可执行配置

  3. 自行拼接参数

    字段、组合或默认值来自猜测

  4. 昂贵执行启动

    早期门槛不足，问题没有被拦截

  5. 运行后报错

    浪费 GPU 时间与工程师排查时间

问题不只是“回答错了”。

系统缺少一个在执行前把隐含约束转成机器可检查规则的地方；模型自己判断“这份 JSON 看起来合理”不能充当验证器。

延迟失败 · 额外 GPU 成本

增加更多上下文

可能改善能力发现：提供仓库地图、相关代码和调用点。但大量源码可能仍然缺少明确的适用范围、互斥关系和前置条件，也会引入检索噪声。

发现问题不保证合法

增加能力契约 + 预检

把已知规则明确表达出来，并用确定性校验拦截不符合规则的配置。它无法凭空补齐未知规则，所以需要代码证据、测试和领域工程师共同维护。

这些项目提供的是不同层面的积木，而不是一个可以直接解决内部库理解与 Recipe 生成的完整系统。推荐组合现有工具，并自建少量领域契约。

Aider · Repo Map

aider.chat ↗
借鉴模式

把关键类、函数、签名与依赖关系压缩成代码地图，并按任务相关性选择上下文。适合解决“Agent 不知道能力在哪里”。

用来做内部仓库索引与相关代码检索的设计参考；不必为了 Repo Map 直接替换 Harness。

Griffe

mkdocstrings.github.io ↗
优先试用

从 Python 源码或运行时对象提取模块、函数、类、参数与文档信息，并可序列化为 JSON、比较 API 变化。

用来做本地生成 API skeleton 与签名清单；不要期待它自动发现所有领域语义。

JSON Schema / Pydantic

json-schema.org ↗
优先采用

为 JSON 结构、字段类型、必填项和可枚举值提供确定性验证。Python 侧可选 Pydantic 组织模型与校验逻辑。

用来做Recipe 结构校验的硬门槛；跨字段业务规则仍要自己实现。

Repomix

repomix.com ↗
快速 PoC

将代码库整理成适合 LLM 分析的上下文，也提供 MCP 模式。其 MCP 文档目前标为实验性；CLI 可本地处理代码，但代码发往哪里取决于后续模型调用。

用来做一次性本地仓库梳理；过滤敏感文件、审查输出，只连接批准的内网模型。

Promptfoo

promptfoo.dev ↗
优先评估

为模型或 Agent 建立可重复测试集，检查结构、行为、成本、延迟与多次运行的差异。可用本地 CLI 和内网模型服务执行。

用来做比较 Baseline / Repo Map / Contract / Combined 四种路线，而不是凭演示印象决策。

MCP

协议规范 ↗
继续使用

标准化发现和调用工具，并提供 Resources / Prompts 等原语。它能承载契约查询，但协议本身不定义你们量化库的业务约束。

用来做作为可选传输和集成边界；同进程能力可先用 Python 函数直接调用。

LangGraph

GitHub ↗
后续再看

面向有状态、长时间运行、可恢复并需要人工介入的 Agent 工作流。它不负责发现内部 API 或自动生成量化库业务规则。

用来做只在当前 Harness 无法承担持久状态、检查点或恢复需求时再评估。

Agent Skills 标准

agentskills.io ↗
继续使用

把专门知识、流程、脚本和参考资料封装成可复用 Skill。2026-10-22，Anthropic 宣布将该开放标准捐赠给 Agentic AI Foundation。

用来做保留专家 Skills 的领域流程；契约层补充可机器校验的事实，不用它替代 Skills。

项目定位来自各自公开文档。这里的“优先采用 / 借鉴 / 暂缓”是结合你们需求作出的架构判断，不是项目维护者的推荐。

模型负责推理，
契约负责约束。

建议先不改变 DeepSeek Harness，也不要求其他团队重写 Skills。新增一层轻量的 Library Intelligence：将源代码可提取的事实自动整理，再用你们自己的元数据表达隐含的业务约束。

Target state / first iteration

从内部代码到可信的执行入口

左侧是参考输入；中间将可发现性与能力契约结合；右侧是确定性校验与运行。领域规则留在版本化适配层维护。

Important boundary：契约层不一定要变成新的微服务。PoC 可以只是一个本地 Python 包 + 版本化 YAML/JSON 元数据 + CLI validator；当它需要跨进程或跨团队复用时，再把查询接口暴露为 MCP。

把“怎么用”
写成机器可读的契约。

源码分析工具能提供“函数存在、签名是什么、在哪里实现”；但“哪个芯片/runtime 支持它”“哪些字段互斥”“什么条件下禁止运行”往往仍需要团队补充。能力契约把两类信息合并，并绑定到库版本。

Proposed contract / 示意字段

一个契约应该能回答 6 个问题

下面是建议的元数据设计，不是你们底层库的真实 API，也不暗示这些约束已经存在。

  • identity能力 ID、契约版本、仓库 commit、owner
  • implementation真实模块/符号、参数签名、源码定位
  • applicability模型族、目标平台、runtime、precision 的支持范围
  • preconditions必须先完成的步骤、必需文件/数据、互斥组合
  • examples通过校验的最小样例、已知失败与负例
  • validationSchema、业务规则、dry-run 命令、证据与测试引用

  commit: <git-sha>
  symbol: <module.function>

  targets: [<validated-target>]

  - <required-prior-step>

    severity: error

    message: <actionable explanation>

  schema: <schema-ref>

Illustrative metadata only. The contract should point to real source / tests and must be pinned to the library revision used for each run.

机器可以自动提取的内容

包与模块结构、公共函数、签名和类型、docstring、部分默认值、测试定位、Git 版本差异。Griffe 是可研究的起点；Aider Repo Map 是相关代码图谱的设计参考。

自动化可随版本重建

必须显式维护的业务事实

芯片/模型支持矩阵、参数交互约束、风险等级、必要前置条件、有效与无效的真实案例。可先由领域工程师维护在自己的 adapter/metadata repo，不依赖底层库团队配合。

人工确认引用证据

先校验 Recipe，
再启动 GPU。

不要让同一个 Agent 同时担任“配置作者”和“最终验证者”。Recipe 由 Orchestrator 生成；预检器是确定性工具，返回机器可读、可定位的错误；Orchestrator 可以据此有限修正，再重新预检。

结构校验

JSON 解析、必填字段、类型、枚举、范围与字段是否拼错。由 JSON Schema / Pydantic 等确定性验证。

输出：字段级错误

语义校验

跨字段约束、平台兼容性、必需先决步骤、互斥配置与支持矩阵。来源必须指向已确认规则或测试。

输出：规则编号与解释

环境 / Dry-run

依赖版本、路径、文件是否存在、权限、目标设备/工具可用性。库没有 dry-run 时，先做安全的薄预检，而非假装已完整验证。

输出：阻断、警告或可执行

错误应该是结构化的

例如返回 rule_id、JSON Pointer、严重级别、实际值、期望条件、证据出处和建议动作。比返回一段含糊的自然语言 traceback 更容易让 Agent 修正。

限制修正循环

允许有限次修正（例如最多 2 次），保存初稿、每次差异、校验输出和最终配置。出现未知规则、互相矛盾的专家建议或高风险变更，转人工而不是无限重试。

!
Fail closed on critical unknowns

如果配置涉及契约不覆盖的高风险参数组合、未知的目标支持范围或无法确认的前置步骤，应阻止执行或进入人工审批。低风险提示可以警告，关键约束不可以靠模型补猜。

先做小型实验，
再决定是否推广。

从一个内部 Python 仓库、少量高频量化/适配能力与历史 Recipe 开始。先离线生成 JSON 并预检；不必一开始就启动完整 GPU/设备流程。只对少量代表任务进行真实执行，以验证预检与真实 runner 的相关性。

实验分组

同一模型、同一任务集、同一执行预算；变化只在能力上下文和契约机制。

建议规模

先取 20–30 个具有代表性的历史任务；每组重复 2 次。此规模是 PoC 起点，不是统计显著性保证。

Baseline

当前 Skills + MCP

只使用现有流程与常规提示，建立当前首次生成成功率的基准。

Local retrieval

加本地 Repo Map / API 检索

测试“让 Agent 找得到代码”单独带来多少提升。

Contract + preflight

契约 + 确定性预检

测试“清晰支持约束和校验”单独带来多少提升。

Combined approach

本地检索 + 契约 + 预检

测试完整闭环。目标是判断组合是否优于单独加检索或单独加校验。

度量操作定义为什么重要
首次生成成功率 主指标第一份 JSON 在没有人工编辑、也没有 Agent 自我修正的情况下，通过结构与语义预检。直接衡量一次生成质量；同时记录每类失败原因，避免一个总数字掩盖问题。
首次执行成功率在选定的代表性子集上，第一份 Recipe 直接通过真实 Python runner 的早期检查并执行成功。防止预检器只学会“让自己通过”，却无法预测真实执行。
非法字段 / 参数率未知字段、虚构参数、类型错误、无效组合的发生率。验证能力契约能否减少 Agent 自行臆造和拼接 API 的情况。
修正轮次与耗时生成到预检通过的修正次数、模型调用、token、墙钟时间；真实 run 时间单独统计。防止通过大量自我修正提高成功率，却扩大总体成本。
契约维护成本领域工程师新增 / 更新契约与回归样例花费的时间。确认自动提取与人工维护的边界，在工程收益与维护负担之间做取舍。
关键错误漏检数人工标注为 critical 的问题却被预检器放行的数量。安全门槛。PoC 应力争为 0；任何漏检都要归类并补规则。

控制变量：固定内网模型版本、系统提示版本、温度/采样设置、可用工具及最大调用预算；任务顺序随机化；盲评最终 Recipe。预检失败和真实执行失败要分开记录，避免把“没有报错”误当成“模型质量达标”。

先定义结果，
再决定是否推广。

建议先以“契约机制”为核心 PoC 候选，但不承诺它必然胜出。以下阈值是为团队第一次决策提出的暂定门槛，必须在看到数据前确认，不能称为行业标准。

继续推进的暂定条件

完整方案 D 相对 Baseline 首次生成成功率提升至少 15 个百分点；关键错误被预检放行数为 0；收益不是通过无限增加修正轮次取得；契约维护成本处于团队可接受范围。

暂停或调整的条件

若 D 没有稳定优于 B 或 C，或提升只体现在 JSON 格式、对语义/真实执行无改善，应停止扩展架构；先定位误差来源，而不是继续堆检索或更多 Skills。

Counter-hypothesis A

错误主要来自需求缺失，而不是库知识

若客户任务未提供目标 runtime、设备或 KPI 门槛，再好的契约也无法推导未知输入。需要任务澄清和需求完整性检查。

Counter-hypothesis B

契约不完整或过时

若关键约束散落在分支条件或测试外，契约可能给出错误安全感。必须绑定 commit、来源和测试，版本变化触发重验。

Counter-hypothesis C

模型推理与多步规划才是瓶颈

如果能力已被正确发现、契约也足够明确，而模型仍无法根据专家结论选择正确流程，才应优化规划策略、提示、模型或使用确定性模板。

Counter-hypothesis D

规则维护成本高于收益

若只对极少数低频 API 有用，不要给全仓库建契约。仅覆盖高频、高失败成本、高隐含约束的能力节点。

一个有用的决策原则：契约不是替代模型推理，而是压缩模型必须猜测的部分。若某个规则能用代码明确判断，就不要让 LLM 一再推理它。

从一个失败案例开始。

PoC 最小化：一份内部库、一种量化/适配场景、一套契约、一组真实任务、一个预检入口。先证明收益，再决定是否推广至其他 Skills、平台和设备。

  1. Days 1–2 / 定基线

    选任务，收集失败样本

    从历史 Recipe Register 挑选 20–30 个任务；收集已验收配置、运行日志和已知失败。人工标注关键约束与成功判据，并冻结当前流程版本。

  2. Days 3–5 / 建索引与契约

    Griffe + Repo Map 思路 + 手工业务元数据

    本地扫描目标仓库、生成 API 索引和代码引用；优先为少量高风险步骤补充支持矩阵、前置条件、有效/无效案例与版本 pinning。

  3. Days 6–8 / 接入 Orchestrator

    提供查询与校验接口

    先用受控 Python API 或 CLI，暴露能力查询、合同读取、示例查询与 validate_recipe。仅在需要跨进程 / 多客户端时包装为 MCP tools。

  4. Days 9–10 / 对照评测

    跑 A/B/C/D 四组实验

    记录首稿、校验错误、修正轮次、模型开销与真实执行结果。复核关键漏检；产出是否继续投资的明确结论。

  5. After PoC / 扩大范围

    只推广已证明有效的模式

    对被证实有收益的能力类别加契约模板和版本检查，再推广到其他 Python 仓库；Recipe Register 保存契约版本、Run 证据、Artifact digest、端侧指标与人工审批。

明确不做

不重写 DeepSeek Harness；不让其他团队修改自己的 Skills；不将源码发送到公共托管服务；不从全仓库代码知识图谱和复杂多 Agent 系统起步；不在首轮 PoC 里要求完整设备农场闭环。

最小交付物
