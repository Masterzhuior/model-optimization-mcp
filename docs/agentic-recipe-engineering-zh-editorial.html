一份面向平台下一阶段的设计简报

Agentic
Recipe Engineering

让 Agent 理解、操作并改进内部模型优化库，而不是把每一个错误 Recipe 都变成一次数小时的实验。

场景：4B decoder-only LLM · Chip A · INT8 · 可信内部用户 · 离线 / 内网运行
01 — 核心判断

Recipe 不是最难的部分。

现在的 Recipe 结构已经能够表达模型、库版本、目标芯片、Stage、依赖和质量门。真正的问题是：Agent 仍然可能在不了解内部库语义、历史失败和端侧反馈的情况下，生成一个“格式正确但判断很差”的 Recipe。

真正要建设的不是一个更会写 YAML 的 Agent，而是一个能够基于证据形成、验证和修正工程判断的 Agentic 决策系统。
Agentic layerDecision flowFeedback loop
02 — 真实痛点

真正昂贵的不是报错，而是“成功运行但不可用”。

一次 GPU Run 需要 3–6 小时，端侧评测还要约 30 分钟。格式错误应在本地快速失败；更危险的是量化流程成功结束，却出现端侧精度下降。

运行预算是约束，不是重试额度：失败任务不能原样再次提交；每一次尝试必须是一条新假设，并且能说明改了什么、为什么改。
03 — Agentic 闭环

把 Onboarding 变成一个有边界的实验推理系统。

推荐的不是完全自由的 Autonomous Agent，而是“固定边界 + 动态判断”：平台控制不可逾越的边界，Agent 负责探索、解释、选择和提出下一步。

04 — 内部库环境

不要把 internal-lib 做成一份大文本；把它做成 Agent 可以探索的环境。

OpenHands 和 SWE-agent 最值得借鉴的不是整套产品，而是 Agent–Environment Interface：Agent 通过工具逐步探索工作区、执行探针、观察反馈，而不是预先接收全部代码。

Capability Card

这个 Stage 做什么，输入输出是什么，哪些版本和目标可用。

Source Evidence

参数在哪里被解释，谁调用它，哪些测试和异常路径相关。

Case Evidence

相似模型和芯片过去为什么成功或失败，工程师改了什么。

05 — 工具接口

工具接口决定 Agent 是工程师，还是会写 YAML 的猜测者。

inspect_library_context

获取所选库版本、Stage、运行入口、环境事实和知识缺口。

inspect_stage

获取 Stage 输入输出、参数、版本差异、调用者、测试和失败模式。

inspect_model

提取结构、算子、shape、参数规模和目标芯片风险信号。

search_similar_trajectories

搜索完整决策轨迹，而不是只搜索成功 Recipe。

explain_source_symbol

返回有限源码片段、相关符号、测试和版本限制。

preflight_recipe

在真实库环境执行轻量探针，把“已知、未知、未证明”分开。

diagnose_run

结合日志、Stage 状态、量化误差和端侧指标给出下一步动作。

diagnose_run(run_id="run-042") → category: QUALITY_FAILURE → likely_stage: quantization → evidence: ["attention output error increased"] → allowed_mutations: ["exclude_modules", "approved_clip_parameter"] → forbidden_mutations: ["model.revision", "quality_gate"] → remaining_budget: 2
06 — 失败诊断与记忆

失败诊断不是解释报错，而是生成下一步行动。

未来 Agent 学到的不是“batch size 通常是 8”，而是：在这个模型、芯片、库版本和校准集下，8 曾经造成什么现象；为什么改成 4；端侧结果是否真的改善。

人工修正不是失败后的备注，而是 Agent 学习工程判断的高价值监督信号。
07 — 开源借鉴与落地

每个项目放在它最擅长的层。

项目 / 模式借鉴价值定位
OpenHands / SWE-agent工具驱动的环境探索、工作区和可回放轨迹。参考 Agent–Environment Interface
PydanticAI类型化工具、依赖注入、结构化决策、轨迹评测。优先做 Agent 层原型
LangGraph持久化状态、条件分支、人工介入和长流程。承载 Agentic Loop
ModelOpt / ORT / AIMET量化、校准、误差定位等领域能力。作为工具或执行 Stage
Optuna / Ray Tune / MLflow有限搜索、试验状态、证据和制品血缘。后期搜索 / Evidence Plane
第 1–2 周：离线 Agent Benchmark

用历史任务评估工具选择、版本意识、证据使用、失败定位和停止行为。

第 3–6 周：Library Environment + Critic

实现库探索、源码证据、相似轨迹和候选 Critic，不提交真实 GPU。

第 7–10 周：Diagnostician + Preflight

让 Agent 能从真实库环境获得事实，识别不确定性并生成受控 Mutation。

第 11–12 周：受控执行

只允许 1–3 个有证据的候选，比较无效 Run、首次成功率、端侧达标率和人工时间。

汇报结论：我们不再把 Agent 当成 Recipe 文本生成器，而是把它放进一个可探索的内部库环境中，让它基于源码、历史轨迹和真实运行反馈形成证据驱动的候选方案，并用固定边界控制昂贵的 GPU 实验。
