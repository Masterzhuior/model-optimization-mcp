v1.2 thesis

Do not build a multi-agent platform first.

Multi-agent is a search operator, not an architecture. Onboarding is serial and context-heavy; keep one owner, parallelize only evidence and diagnosis.

No oracle, no experiment. A mock pipeline can validate the harness, not the hypothesis.

00
Executive decision

Prove the bottleneck before choosing the topology.

The unit of work is a real onboarding job, not a chat transcript. The question is which change reliably improves first-attempt verified success — and through which mechanism.

01 Four search spaces02 L0–L4 topologies03 Owner + scouts04 T09 / T1005 MAST + Who&When06 pass^k + cost07 Screening vs confirmation08 Action-space schema09 Evolvable vs frozen10 Stage gates
Goal

Raise first-attempt verified success

A Recipe that executes, reaches the device, and meets quality gates — without hidden repair, retries, or best-of-n.

Two scoreboards

Reliability ≠ optimization quality

A. Can the agent discover, compose, preflight, execute and deploy? B. Among valid runs, which Pareto trade-off is better?

Non-goals

No agent framework, no shared memory, no new MCP layer yet

Those are confounding variables until the baseline shows they are needed.

v1.2 change: the experiment factor is no longer “more agents”; it is search space × topology × knowledge intervention. Change one at a time.

01
Problem reframing

“Which agent wins?” is a weak question.

A winner can be a lucky sample. A repeatable failure pattern is actionable engineering evidence.

HypothesisWhat it looks likeFirst intervention
H1 Skill ambiguityMandatory constraints and suggestions are mixed; triggers are unclearGEPA / Skill patch
H2 Capability opacityFunctions exist, but signatures, defaults, preconditions and failure semantics are hiddenRepo map / contract
H3 Validation gapInvalid configs reach expensive executionPreflight
H4 Orchestration noiseInconsistent Skill outputs, too many tools, conflicting evidenceOwner decision / fewer roles
H5 Objective confusionJSON emitted ≠ executed ≠ device pass ≠ quality passGate sequence
H6 Optimization varianceCalibration, device, runtime, seeds, contentionFixed protocol / repeats
H7 Search-space mismatchTeam optimizes prompts while the bottleneck is workflow or parametersFour-space routing
Do not fix while measuring. The first run preserves the current implementation, adds instrumentation and isolation, and changes nothing else.
02
System under test

Benchmark the whole path, but label every boundary.

The agent’s text is one intermediate artifact. The verified result is the unit.

01 / REQUESTModel, target, quality constraints, calibration data.
02 / EVIDENCESkills, repo, dataset, device profile.
03 / RECIPEFull JSON from evidence and supported options.
04 / PREFLIGHTSchema, capability, compatibility, resources.
05 / EXECUTErun(config), logs, artifacts, failure class.
06 / DEVICERuntime, accuracy, latency, memory, power.

Every stage emits a timestamped, machine-readable event.

Recipe → preflightRepair only with actionable diagnosticsSchema, capability lookup, compatibility, dry-runErrors, warnings, duration, repair count
Preflight → executeCall the supported entry pointIsolated workspace, pinned deps, resource limitsCommand/API, exit code, stdout/stderr, artifact hash

Real-system rule: the Arena needs a real run(config), real assets, and a device/KPI oracle. A simulation can validate the harness; it cannot validate the hypothesis.
03
Four search spaces

Optimize the right object, not the most visible one.

“Optimize onboarding” can mean four different things. Mixing them in one loop makes the experiment uninterpretable.

SpaceOptimizeOptimizerArtifactEvaluator
S1 Solutionbits, group size, calibration, mixed precision, exclusions, backendAIDE / AgentHPO / Optunarecipe.json candidatesQuality / latency / memory Pareto
S2 Workflowstages, tools, order, branchesAFlow (MCTS)workflow JSONGate sequence + cost
S3 Instructiontriggers, steps, evidence requirements, stop conditionsGEPA / ACESKILL.md / playbook versionSuccess + cost + groundedness
S4 Implementationrunner, adapter, diagnostics, cachingDGM / AlphaEvolvecode patchFull regression + sandbox
Order

Cheap → expensive

S3 instruction → S2 workflow → S1 parameters → S4 implementation. Start where the failure is, not where the tool is fashionable.

Rule

One space per experiment

Do not change Skill and workflow in the same round. Contracts and evaluators are outside every search space.

04
L0–L4 topology

Multi-agent is a topology choice, not a goal.

Independent replicas, role teams, pipelines and populations answer different questions. Do not call them all “multi-agent”.

LevelWhat it isQuestionMetricMain risk
L0Single agentIs the task hard?First-attempt successCapability ceiling
L1Independent replicasHow large is the variance?pass@k / pass^kNot collaboration
L2Owner + scouts + critic + diagnosticiansDoes division of labour reduce failure?Success, coordination failuresHandoff loss
L3Pipeline of specialistsIs specialization/parallelism worth it?Gate conversion, wall-clockContext fragmentation
L4Population / evolutionWhich config/workflow/skill is better?Effect size + costOverfitting, evaluator gaming
Recommended for onboarding

One decision spine, parallel periphery

Use L2: a single owner holds task/recipe state; scouts read in parallel; a critic checks preflight; diagnosticians propose one mutation each. Keep L3 for interface-clean stages only.

When not to use multi-agent

Serial, coupled, or unmeasured

Recipe → compile → device is a serial coupling. If coordination cost exceeds the gain, or there is no trustworthy evaluator, stay at L0/L2.

External evidence: Anthropic reports a large gain for multi-agent breadth-first research at roughly 15× token cost; Cognition warns that peer multi-agent coding/long-context tasks fragment context. The lesson is placement, not ideology.
05

Keep one decision spine. Parallelize evidence and diagnosis.

Do not start with twenty arbitrary prompts. Choose tasks that separate discovery, validation, execution and quality failures.

Discovery

3 tasks

Find the dominant failure modes. 5–10 repeats.

Validation

2 tasks

Confirm an intervention. 10–20 repeats or paired design.

Held-out

2–3 tasks

Used once, at the end. No tuning on it.

07
Metrics & statistics

Two scoreboards, five gates, no magic score.

Separate engineering reliability from optimization quality. Report distributions and cost, not a single best run.

Scoreboard A

Engineering reliability

First-attempt verified success; G1–G5 conversion; pass@1 / pass@k / pass^k; repair burden.

Scoreboard B

Optimization quality

Quality, latency, memory, size; feasible Pareto frontier; fixed device/runtime protocol.

MetricDefinitionWhy it matters
First-attempt verified successG5 without human repair or a second RecipeClosest to the product goal
pass@k / pass^kAny of k succeeds / all k succeedCapability vs reliability
Cost per verified successTokens + GPU-min + wall-clock + human timePrevents “eventual success”
Coordination failuresHandoff, duplicate work, conflict, churnMakes multi-agent cost visible
GroundednessCritical parameters with cited evidenceReduces plausible but unsupported configs
GeneralizationHeld-out task pass ratePrevents overfitting the example
Screening

3 × 5

Find gross failure modes. Do not rank interventions from this.

Confirmation

2 × 10–20

Paired tasks, bootstrap 95% CI, mixed-effects.

Stop rule

No held-out gain

Or cost per success worsens. Stop; do not add agents.

Coordination taxonomy (MAST)

Specification · misalignment · verification

Handoff loss, ignored input, duplicate work, decision conflict, premature termination, incomplete verification, evaluator bypass.

Attribution

Who&When + ablation + replay

Predict the responsible agent/step; remove one role/tool; replay the failing step with oracle evidence. No self-report as the only evidence.

Output: {earliest_boundary, mast, responsible_agent_step, evidence, confidence, candidate_intervention}. This is the input to the next patch.

Cheap screen

Schema · compatibility · small eval

Stop infeasible candidates before expensive device runs.

Expensive confirm

Pinned device · warm-up · repeats

Fixed inputs, versions, protocol, artifact hashes. Report Pareto, not one score.

Action-space rule: every field has a source, a constraint and a preflight check. The agent may choose among supported values; it may not invent an API.
12
Security & plan

Local execution is not local-only data flow.

The data boundary covers code, prompts, telemetry, logs and artifacts — not just the CLI process.

ThreatControl
Agent reads unrelated filesRead-only repo, minimal workspace, path allowlist
CLI sends context outApproved internal endpoint, network policy, telemetry audit
Concurrent runs overwrite configPer-run directory, no shared writes
Stale artifacts reusedArtifact hash + run ID
Untrusted Skill/repo contentTool permissions, command allowlist, review
Evaluator tamperingExternal read-only evaluator, version check
GPU contention distorts metricsLease, exclusive access, fixed protocol
Log leakageRedaction, retention, access control
Week 1

Freeze + baseline

Pin commit/Skills/deps/model/evaluator; run L0 + L1 on T01–T03; build trace and evaluator.

Week 2

Topology screen

L0–L3, 3 tasks × 5 reps; code coordination failures with MAST; decide whether multi-agent helps at all.

Week 3

Knowledge intervention

On the winner: repo map, contract, preflight — one at a time. Measure gate conversion and repair burden.

Week 4

Search + confirm

GEPA / AFlow / MaAS / AIDE on held-out; 10–20 reps; promote only reproducible gains.

Stop rules: no held-out gain; coordination cost exceeds benefit; cost per verified success worsens; failures are infrastructure/evaluator noise.

Final recommendation

Start with a benchmark, not a platform rewrite.

Run five to ten independent attempts on one frozen onboarding task. Classify the earliest boundary. Change one layer. Confirm on a held-out task. Only then decide whether the next investment is a Skill, a contract, a workflow, a topology or a training loop.

BASELINE WORKER

Inspect, then compose

Inspect repo/Skills; do not assume an API. Use supported capabilities. Write recipe.json under the run dir. Preflight before expensive runs. Do not edit the evaluator, baseline, or other runs. No success claim without machine evidence.

OWNER

One decision spine

Hold task/recipe/budget. Ask scouts for evidence and diagnosticians for one hypothesis each. Choose only grounded recipes. On failure: repair, replace, or stop. Never edit the evaluator.

CRITIC + DIAGNOSTICIAN

Frozen rubric, one mutation

Critic: pass/fail + diagnostics, no edits. Diagnostician: one root cause + one mutation, with trace evidence and a rollback path.
