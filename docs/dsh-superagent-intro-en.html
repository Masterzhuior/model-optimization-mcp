dsh-superagent

A proactive coding agent for a single GitHub repository, shipped as a bundle for DeepSeek Harness. It listens to GitHub (and optionally Feishu); when an allowed person asks, it opens a work item, does the work in its own session and directory, and answers in the original conversation — e.g. with a pull request. Its whole creed fits one line: take as little human attention as possible, give as much value as possible.

What is it, in one line?

Think of it as "an outsourced teammate who lives in your repo and shows up when called." Someone on the allow-list comments @agent fix this bug on an issue; the agent checks out code in its own directory, changes it, verifies it, then pushes a PR right back into that same issue. It mostly leaves you alone in between — until it needs your decision, or the work is done.

Plain English
A traditional agent is a "Q&A machine"; an agent that can act for a whole team can also "generate noise for a whole team." dsh-superagent is "hand it a task, it works on its own and delivers the result, without chatter in between." And it only responds to authorized people and only does work within an authorized scope — not anyone can command it, and it won't freelance.
📡

Listens, doesn't nag

Runs as a DeepSeek Harness bundle, listening to GitHub (Feishu optional). Event-driven, not something you trigger by hand.

🎫

Every ticket is authorized

No work starts without a Mandate. Authorization comes from "an allow-listed person asks" or "a rule the team wrote."

🤫

Speaks only at key moments

Confirms once before big work; stays quiet while working; speaks again when a result is ready, a decision is needed, or it can't finish.

2

Core philosophy: least attention, most value

30s: Score every component by how much attention it costs you; cut it if the math doesn't work.

Every part of the project is scored by how much attention it costs you. A message, a notification, a question, a setting, a panel element, a paragraph of docs — each must give more value than the attention it consumes, or it is removed. That is the design's master rule.

Rules it holds the agent to

🚦 Acts only when asked, or a written rule allows

A request must address the agent directly and come from an allowed person. Unrequested work needs a team rule, and starts in a mode that only records what it would have done.

🤐 Speaks only when a person must act or can use a result

Confirms a request once, naming what it will do; stays quiet while working; writes again when a result is ready, a decision is needed, or it can't finish.

❓ One concrete question at a time

Asks in a structured form so the question reaches the person instead of being buried in a long report.

🛑 Stops by impact, not by effort

A local change goes as far as a reviewable result. A change needing a design decision stops with a clear question.

📋 Reports honestly

A draft is marked unfinished, a failure is reported as a failure, and a limit is never bypassed just to avoid asking.

🧩 Few concepts, few settings

A business need becomes an attribute of a domain concept, or a prompt the agent follows; a good default replaces a setting.

Responsibility reminder for operators
The agent comments, opens PRs and messages people under accounts your team sees every day — every message costs your colleagues' attention, and you are responsible for it. Advice: ① start narrow (short allow-list + proactive work recorded only); ② when it's noisy, tighten the prompts or pause — don't add more messages to explain the noise; ③ don't use it to produce volume (mass PRs, broadcasts); ④ read, correct and own what it posts in your name.
3

Domain model: minimal but self-consistent

30s: Just five concepts (Source / Trigger / Thread / Eval / Ticket) explain the whole collaboration; business needs are merely their attributes.

The code, tools, panel and docs all use the same vocabulary. Following the philosophy, the model holds only the concepts the work needs; a business need becomes an attribute of a concept, not a new concept. Here is the core flow: a Source produces Triggers → Triggers aggregate into Threads → Eval decides whether to open new work → a Ticket is handed to an Executor → results return to the Source through a Channel.

Five "core concepts" + what they guard

ConceptWhat it isRules it keeps / why it exists
SourceAn event stream. A kind (reusable impl) + one instance (config)Holds its read position and bot identity; translates platform events into Triggers and Threads; drops its own messages and unrelated triggers. no replay on restart
TriggerOne immutable event with the Source's own metadata (e.g. actor)Belongs to one or more Threads; accepting the same trigger twice makes one Ticket. unit of audit & idempotence
ThreadTriggers in time orderAt most one Eval runs on it at a time; may hold several Tickets; holds Subscriptions, the running Eval, Decision history. consistent view for Eval
EvalJudgement on a batch of Triggers, two layers: gate + assessmentStateless. Inputs a trigger batch / thread snapshot / tickets / policy; outputs a Decision. decides if work starts
TicketA unit of authorized workOnly Eval creates one; references a Mandate; holds Channels and Inputs; defines its own state (not the Executor's). owns execution & reports

Supporting concepts: Mandate (what an accept grants — why and how far), Assignment (binding a Ticket to one Executor instance), Subscription (many-to-many Ticket↔Thread), Channel (the write side of a Thread), Correlation (adds context only, never routes).

Plain English
A "person" is not a domain concept — just metadata on a Trigger. The allow-list is a Source's part of the Policy; cross-platform account mapping is prompt text the agents read. The design deliberately avoids making "person," "membership," or "cross-Source mapping" into entities, keeping the model tiny.
4

Authorization: who can make it work, and how far?

30s: No work without a Mandate; allow-list, rules and strength triple-gate it — and chat content can never change permissions.

A Trigger enters the system by two paths: either through Eval (deciding whether to start new work) or through Subscription (continuing existing work). The host enforces allow-lists, rules and Mandates; messages and quoted docs are inputs to a decision, never able to change permissions.

🆕 Path A: new work (via Eval)

The Source records whether a message addresses the agent (mention = @, direct = DM). The gate checks sender + that Source's Policy:

  • An allowed person who @s it → explicit request
  • A follow-up on a Thread with Tickets → follow-up rules apply
  • Anyone else → the admission table decides if it becomes a candidate
  • A bot on the bot list → only an inferred candidate, never explicit

🔁 Path B: continuing work (via Subscription)

Every message on a subscribed Thread (including bots and CI) is delivered to its Tickets as context, bypassing the gate and granting no new authority. The Ticket stays limited by its Mandate.

  • A person's follow-up on "its own Thread" → the Executor decides
  • The Executor handles in-scope work, hands back what's out of scope
  • Bots/CI never wake an ended Ticket
  • Mandate is withdrawn only by a person's stop or failed revalidation

Three "strengths"

StrengthTypical cases
explicitA listed person @s it / follows up on a Thread that has a Ticket / a cell of the admission table set to explicit
inferredAn unlisted person follows up on a Thread with a Ticket / a table cell set to inferred candidate / a bot on the bot list speaks
not admittedAny other bot's message / anything the admission table ignores / any inferred case while mode is off

Accept mode: a three-step "proactiveness" switch

off

No inferred candidate is admitted (unaddressed messages, bot messages, unlisted follow-ups). Explicit requests always work.

observe (default)

Inferred candidates are assessed; a positive assessment is recorded as "would accept" and ignored — not actually worked. Use this first to see what it would do.

auto

A positively-assessed inferred candidate is accepted directly. Switch here only after reviewing the recorded Decisions.

Recommended starting posture
Begin in observe; after reviewing the recorded Decisions, switch to auto. Every proactive accept needs at least one matching rule; a rule describes a kind of proactive work, and its process/communication requirements override that Ticket's defaults (e.g. a rule can name the required reviewer before merge).
5

Execution: how a ticket gets done

30s: Each ticket gets its own Session + directory, opens PRs, follows review/CI itself, and pauses to wait for you if blocked — and resumes after a restart.

Each Ticket gets an Executor Session named worker-<ticket id> and a directory named after the Ticket's short name. The Executor runs commands without approval as the operator's OS user; the worker preset moves foreground shells to background jobs after 5 seconds, so a long command won't block it from receiving new messages.

Ticket stages (top to bottom, first match wins)

Input undelivered · person
Delivering an Input to the Executor Session failed; retried after 2s, then doubling up to 1 min.
Awaiting answer · person
The Ticket has an Attention — the Executor raised one concrete question via human_action.
Awaiting review · person
The latest Report is ready — usually meaning "opened a PR, waiting on you."
Blocked · Failed · person
Latest Report is blocked/failed and no human message since. A new human message releases it back to the Executor.
Queued · working
No Assignment, or a pending one.
Waiting for a Trigger · idle
Latest Report is waiting, or the Assignment ended — turn finished with no open question, waiting for the next trigger.
Working · working
Everything else — actively working.

A person stage means it can't continue without human input; a new human message on a subscribed Thread releases a blocked/failed Ticket to its Executor.

🗂️

One directory per ticket

Before the first Assignment, a prepare command (default git worktree) runs once to build a checkout; a PR belongs to the Ticket when its branch's last path segment matches the Ticket's short name.

⏱️

Worker slots

A Ticket holds a worker slot from launch; if background jobs/subagents are still running at turn end, it keeps the slot and isn't reported as waiting. Background work has at most 30 minutes.

🔀

Merge with restraint

By default it never enables auto-merge as the agent account; Delivery requirements must name another account's CLI for merging. Auto-merge only if: ready + required approvals cover head commit + additions+deletions < 200 lines.

Default auto-merge rule (Delivery requirements)

Rule highlights (paraphrased from the docs, not verbatim)

① By default it never enables auto-merge as the agent account — GitHub attributes the merge to whoever enabled it; to merge, Delivery requirements must name another account's CLI. ② Auto-merge is allowed only when the PR is for this Ticket, is ready, required approvals cover the head commit, and additions+deletions < 200 lines. ③ Before pushing another revision, the Executor withdraws auto-merge. ④ With no merge CLI named, drop the auto-merge paragraph and require manual merge.

Plain English
It's not "spawn a thread and finish." It opens a PR, then tracks that PR's reviews / CI / merge; the Ticket ends only when all its PRs are closed. Human interjections are picked up; out-of-scope ones are handed back; if it can't finish or needs your call, it stops and waits. After a restart/crash, unread messages go back to Eval while read content is preserved — so it "resumes" rather than "runs wild from scratch."
6

Architecture: strict one-way deps + single writer

30s: Strict one-way dependencies, all domain writes go through the Engine, side effects are stored-then-done — so it's easy to reason about and to recover.

Core discipline: src/core touches no I/O and imports nothing external; src/sources does not import src/app; the panel imports types only. All domain writes go through the Engine (the single writer); external side-effects are queued (Effects/Outbox) and executed after the transaction commits. The whole thing runs injected as a DeepSeek Harness bundle.

cordis.patch.yml injected plugins (real excerpt, trimmed)

cordis.patch.yml — bundle layer: inserts plugins and agent presets (from the repo)
# bundle layer: inserts plugins (no config) and the agent preset each Session runs under
- insert:
    - id: dsh-superagent            # main plugin
      name: dsh-superagent
    - id: dsh-superagent-github     # GitHub source
      name: dsh-superagent/github-watch
    - id: dsh-superagent-feishu     # Feishu source (optional, disabled by default)
      name: dsh-superagent/feishu-watch
      disabled: true
    - id: dsh-superagent-worker-preset   # preset of every Executor Session
      name: '@deepseek-ai/dsh-agent-preset'
      config:
        id: dsh-superagent-worker
        name: dsh-superagent worker
        # foreground command moves to background after 5s; only work tools
        plugins: [ persona, agent-instructions, shell, tool-fs,
                   tool-jobs, skill-filesystem, tool-skill,
                   compaction, delegation(subagents), tool-todo ]

🧩 cordis patch

The patch above injects three plugins (main / github-watch / feishu-watch). When the panel or Harness edits config, the host writes the file in place; most settings apply without restart (a save touching Setup fields restarts).

💾 Persistence isolation

Only the Store opens a SQLite file; DeepSeek Harness provides Session/process environment, consumed by this system through narrow interfaces (SourceHost/SessionsHost) with no reverse dependency on its internals.

📨 Effects / Outbox

Relays/launches/deliveries after a decision are stored first, done after: enqueue → execute on commit, with merge, concurrency limits and exponential-backoff retries. A third consecutive failure is reported as a system problem.

Web panel: only surfaces what needs a human

30s: The panel appears only where a human is needed, and puts the action right at their fingertips; healthy states take no space.

Open Superagent in the DeepSeek Harness web sidebar to supervise the agent. The panel prioritizes work that needs a person, then system health and history. It uses domain terms; internal IDs appear only in folded details.

Tabs (ordered along the workflow)

EvalDecisions with their reason and matched rules

Panel design — seven principles (condensed)
Focus on what matters; precise, mutually-exclusive definitions; one place per concept; use domain terms; honest state (count = length of the linked list); quiet by default (healthy states take no space); consistent controls. In one line: appear only where a human is needed, and put the action right at their fingertips.

Tech stack: a restrained TypeScript engineering

30s: A TypeScript project so restrained it has just two runtime dependencies; all host capability comes from DeepSeek Harness.

⚙️ Language & runtime

TypeScript 6 + Node 22.19+ / 24+; package manager pnpm 11.7. Only two runtime deps: proper-lockfile (file lock) and zod 4 (validation).

🧱 Host & plugins

All capability comes from @deepseek-ai/dsh-* peer deps (Harness, Session, Tools, LLM, permission presets, client UI, …), injected via cordis.

🏗️ Build & test

tsdown bundles, vitest 4 tests, tsc --noEmit typechecks. pnpm check = typecheck + test + build in one pass.

🖥️ Panel & storage

The panel uses React 18 (self-drawn controls, no host UI primitives imported); persistence is a single SQLite (orchestrator.sqlite), owned exclusively by the Store.

Quick start: let an agent set it up with you

30s: Let an agent set it up with you — one question at a time, full plan before acting, secrets left for you to do by hand.

Setup has many steps, so the project has your own coding agent do it with you. Just tell it: Read SETUP.md in this repo and set up dsh-superagent with me. It asks one question at a time, shows the full plan once, then installs and configures everything.

SETUP "probe" command (run once, keep the result to itself)

SETUP.md — environment probe before install (verbatim excerpt)
# probe: whatever's missing becomes a plan item, not a question
node -v; pnpm -v; git --version; tmux -V; python3 --version
gh --version | head -1; dsh --version
gh api user --jq .login          # operator's own GitHub login, recommended in Q5
command -v lark-cli             # Feishu CLI (optional)
grep -l -E 'id: dsh-superagent\b' "${DSH_HOME:-$HOME/.dsh}"/profiles/*/cordis.patch.yml 2>/dev/null
1️⃣

Probe the environment

Runs a one-shot probe: node / pnpm / git / tmux / python3 / gh / dsh versions, plus login checks. Whatever's missing becomes a plan item, not a question.

2️⃣

Collect answers one at a time

Questions follow the workflow: ① Sources (GitHub/Feishu) ② Repository ③ Agent account ④ Allow-list ⑤ checkout/commit identity ⑥ auto-merge? Each offers a recommended answer.

3️⃣

Plan → execute

After collecting, it sends one full plan; only after you confirm does it act: you do account/CLI steps first, then it installs & starts, then saves settings and prompts in order.

Prerequisites
Needs Node 22.19+/24+, pnpm, git 2.32+, tmux, Python 3.8+, GitHub CLI 2.48+, and a DeepSeek Harness within the package.json range (plus a model provider). Feishu is optional but requires a separate bot app. It never asks for secrets in chat — steps needing your hands are given as copy-paste commands.

To try it: from an allow-listed account, comment @<agent-login> <your request> on an issue in the repo; within about a minute a Ticket appears on the Overview.

🧭 What problem does it actually solve?

A traditional agent is a "Q&A machine"; an agent that can act for a whole team can also "generate noise for a whole team." dsh-superagent puts "proactivity" in a cage using a minimal domain model + strict authorization + attention economics: it acts only when asked or a rule allows, and speaks only when a person must act or can use a result. It resolves the tension between "runs automatically" and "doesn't bother people" through engineering discipline — and that is exactly why it's worth a careful read.
