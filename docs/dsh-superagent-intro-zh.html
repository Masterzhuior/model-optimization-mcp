说人话
传统 Agent 是"你问一句它答一句"。dsh-superagent 是"你交代一件事，它自己开干、自己交活，中间不啰嗦"。而且它只对被授权的人响应，只做被授权范围内的事——不是谁都能使唤，也不会自作主张。
📡

监听，不轮询你

作为 DeepSeek Harness 的一个 bundle 运行，监听 GitHub（飞书可选）。事件驱动，不是你手动触发。

🎫

每张工单都授权

没有"授权书"(Mandate) 的活它不开工。授权来自"白名单里的人开口"或"团队写好的规则"。

🤫

只在关键点出声

开工前确认一次；干活时闭嘴；出结果、要你拍板、或干不完时才说话。一条消息默认一句话。

2

核心哲学：占最少注意力，给最大价值

30 秒：把"占用你多少注意力"当成每个部件的统一打分标准，不划算就砍掉。

整个项目用"它消耗了你多少注意力"来给每个部件打分。一条消息、一个通知、一个设置项、面板上的一个元素，只要它带来的价值不超过它占用的注意力，就砍掉。这是设计的总纲。

对智能体的几条"规矩"

🚦 只在被要求、或被规则允许时才行动

请求必须直接 @ 到它，且来自白名单里的人。没人要的活，必须有团队写好的规则，且先进入"只记录、不动手"的模式。

🤐 只在"人必须行动 / 能用结果"时才开口

开工前确认一次并说明要做什么；干活时安静；结果就绪、需要决策、或干不完时才再说话。

❓ 一次只问一个具体问题

用结构化表单提问，让问题真正送到人手上，而不是埋在一篇长报告里。

🛑 按"影响"收尾，不按"努力"

一个局部改动做到"可评审"就停；需要设计决策的，留下一个清晰的问题收尾。

📋 诚实汇报

草稿标"未完成"，失败就说失败，绝不绕过限制去避免提问。

🧩 少概念、少设置

业务需求变成某个领域概念的属性，或一段 prompt 文本；能用默认值替代的就不做成设置项。

对运营者的责任提醒
智能体以你团队天天见到的账号发评论、开 PR、发消息——每条都会消耗同事的注意力，你对此负责。建议：① 从短白名单 + 只记录模式起步；② 太吵就收紧 prompt 或暂停，别用更多消息去解释噪音；③ 别拿它刷量（批量 PR、群发消息）；④ 它替你发的，你读、你改、你担。
3

领域模型：一套极简但自洽的概念

30 秒：只用 5 个概念（来源 / 触发 / 线程 / 评估 / 工单）就把整套协作说清楚，业务需求只是它们的属性。

代码、工具、面板、文档都用同一套术语。遵循哲学，模型里只有工作真正需要的概念，业务需求变成概念的属性，而不是新造一个概念。下面是它的核心流转：来源产生触发 → 触发按线程聚合 → 评估决定是否开新工单 → 工单派给执行器 → 结果通过渠道回到来源。

五个"核心概念" + 它们的职责

概念是什么它守的规矩 / 为什么存在
Source 来源一条事件流。一种"kind"(可复用实现) + 一份"instance"(配置)保存自己的读取位置与机器人身份；把平台事件翻译成 Trigger 与 Thread；丢弃自己的消息与无关触发。重启不重放
Trigger 触发一条不可变事件，带来源自己的元数据(如发起人)属于一个或多个 Thread；同一触发被接受两次只生成一张工单。审计与幂等的最小单位
Thread 线程按时间排序的 Trigger 序列同一时刻最多跑一个 Eval；可有多个工单；持有订阅、运行中 Eval、决策历史。给 Eval 一致视图
Eval 评估对一批 Trigger 的判断，分两层：门禁(gate) + 研判(assessment)无状态。输入触发批/线程快照/工单/策略，输出一个 Decision。决定是否开工
Ticket 工单一份"被授权的活"只有 Eval 能创建；引用授权书 Mandate；持有渠道与输入；状态自己定义(不被执行器绑架)。拥有执行与汇报

其余概念支撑这五个：Mandate 授权书(接单授予的"凭什么干、能干多远")、Assignment 派工(工单绑定到某个执行器实例)、Subscription 订阅(工单与线程的多对多关系)、Channel 渠道(线程的写入侧)、Correlation 关联(只补上下文，不路由)。

说人话
"人"不是领域概念——只是 Trigger 上的一段元数据。"白名单"是策略里某个来源的一份配置；"跨平台账号对应"是写给智能体看的 prompt 文本。设计刻意不把"人""组织""跨平台映射"做成实体，保持模型极简。
4

授权模型：谁能让它干活？能干多远？

30 秒：没"授权书"不开工；白名单、规则、强度三重把关，而聊天内容永远改不了权限。

一个 Trigger 进入系统有两条路：要么走 Eval（决定要不要开新活），要么走订阅（延续已有的活）。门禁只认白名单、规则与授权书；聊天内容、引用的文档都只是判断的"输入"，改不了权限。

🆕 路径 A：新建工作（走 Eval）

来源先判断消息是否 @ 到智能体（mention=@提及，direct=私信）。门禁检查发送者 + 该来源的策略：

  • 白名单上的人 @ 它 → 明确请求 explicit
  • 在已有工单的线程上跟帖 → 按跟帖规则处理
  • 其他人 → 走"准入表"决定能否成候选
  • 机器人名单上的 bot → 只能成 推断候选 inferred，不能明确请求

🔁 路径 B：延续工作（走订阅）

被订阅线程上的每条消息（含 bot 与 CI）都会作为上下文送达工单，绕过门禁、不授予新权限。工单仍受自己的授权书约束。

  • 人对"自己线程"的跟帖 → 执行器自己拍板
  • 执行器只处理范围内的事，超出范围就"交回"
  • bot/CI 不会唤醒已结束的工单
  • 只在"人明确说停"或"重新验证失败"时才撤销授权

三种"强度" Strength

强度典型情形
explicit 明确白名单上的人 @ 它 / 在已有工单线程上跟帖 / 准入表中被设为"明确请求"的格子
inferred 推断不在白名单的人在工单线程跟帖 / 准入表设为"推断候选" / 机器人名单上的 bot 发言
not admitted 不受理其它 bot 的消息 / 准入表忽略的内容 / 在 off 模式下的一切推断情形

接受模式 Accept mode：主动程度的三档开关

off 关闭

任何推断候选都不受理（未@的消息、bot 消息、非白名单者跟帖）。明确请求始终有效。

observe 观察（默认）

推断候选照常研判；研判"该接"的只记一条"本会接"的忽略，不真正开工。先用这个看它想干嘛。

auto 自动

推断候选研判"该接"就直接接单。等你看过观察期记录、确认它靠谱后再切到这档。

建议起步姿势
从 observe 起步，审完被记录的 Decision 再切 auto。每条主动接单都需要至少命中一条"规则"(rule)；规则描述一类主动工作，其流程/沟通要求会覆盖该工单的默认行为（比如某规则可指定"必须某人 reviewer 批准才能合并"）。
5

执行模型：一张工单是怎么干完的

30 秒：每张工单一个独立 Session+目录，自己开 PR、自己跟评审/CI，干不完或要你拍板就停下等，重启还能续。

每个工单拿到一个 worker-<工单id> 的执行器 Session 和一个以工单短名命名的目录。执行器以运营者的 OS 用户身份、免审批地跑命令；worker preset 会在 5 秒后把前台 shell 转到后台任务，这样长命令不会卡住它接收新消息。

工单的阶段阶梯（从上往下，先命中谁算谁）

Input 未送达 · person
把输入交给执行器 Session 失败，2 秒后重试，之后退避翻倍直到 1 分钟。
等待答复 Awaiting answer · person
工单上有一个"待人工决定"(Attention)——执行器通过 human_action 抛出一个具体问题。
等待评审 Awaiting review · person
最新汇报是 ready——通常意味着"开了 PR，等你看"。
受阻 / 失败 Blocked · Failed · person
最新汇报 blocked 或 failed，且此后无人消息。新的人消息会把它释放回执行器。
排队 Queued · working
还没有派工，或派工还在 pending。
等待触发 Waiting for a Trigger · idle
最新汇报是 waiting，或派工已结束——这一轮干完、没有未决问题，等下一个触发来续。
执行中 Working · working
其它一切情况，正在干活。

带 person 的阶段 = 没人的输入就走不下去；人在订阅线程上的新消息能把"受阻/失败"的工单释放给执行器。

🗂️

每工单一目录

首次派工前，prepare 命令（默认 git worktree）跑一次，建好 checkout；PR 的分支末段与工单短名匹配即归属该工单。

⏱️

工作槽 Worker slot

工单从启动起就占一个槽；轮次结束还有后台任务/子智能体在跑，就保住槽、不算"等待"。后台任务最多 30 分钟。

🔀

合并有分寸

默认绝不以智能体账号开自动合并；Delivery 要求里要写"用另一个账号的 CLI 来合并"。自动合并仅限：就绪 + 必需审批覆盖头提交 + 增删合计 <200 行。

默认"自动合并"规则的要点（Delivery requirements）

规则要点（非逐字，摘自文档描述）

① 默认绝不以智能体账号开启自动合并——GitHub 会把合并记到开启者头上；要合并，必须由 Delivery requirements 里指定的另一个账号的 CLI 执行。② 只有当 PR 是为本工单开的、已 ready、必需审批覆盖头提交、且增删合计 < 200 行时，才允许自动合并。③ 推送新修订前，执行器先撤回自动合并。④ 没有指定合并 CLI 就删掉自动合并段落，改为人工合并。

说人话
它不是"开个线程跑完就完"。它会自己开 PR、自己跟踪 PR 的评审/CI/合并，PR 全关了工单才算完；过程中人插话它会接、超出范围它交回；干不完或要你拍板就停下等。重启/崩溃后，未读消息会回到 Eval，已读内容保留——所以它"断点续传"而不是"从头乱来"。
6

系统架构：严格单向依赖 + 单一写入者

30 秒：依赖严格单向，所有领域写入只经 Engine，外部副作用先存后做，所以易推理、易恢复。

核心设计纪律：src/core 不碰 I/O、不 import 外部；src/sources 不 import src/app；面板只 import 类型。所有领域写入只经由 Engine（唯一写入者），外部副作用先入队(Effects/Outbox)，事务提交后再执行。整个东西作为 DeepSeek Harness 的一个 bundle 注入运行。

cordis.patch.yml 注入的插件（真实片段，已精简）

cordis.patch.yml — bundle 层：插入插件与 Agent preset（摘自仓库）
# bundle layer: 插入插件（无配置），以及各 Session 运行的 agent preset
- insert:
    - id: dsh-superagent            # 主插件
      name: dsh-superagent
    - id: dsh-superagent-github     # GitHub 来源
      name: dsh-superagent/github-watch
    - id: dsh-superagent-feishu     # 飞书来源（可选，默认关闭）
      name: dsh-superagent/feishu-watch
      disabled: true
    - id: dsh-superagent-worker-preset   # 每个执行器 Session 的 preset
      name: '@deepseek-ai/dsh-agent-preset'
      config:
        id: dsh-superagent-worker
        name: dsh-superagent 执行器
        # 前台命令超 5 秒转入后台；只含执行工作所需的工具
        plugins: [ persona, agent-instructions, shell, tool-fs,
                   tool-jobs, skill-filesystem, tool-skill,
                   compaction, delegation(子智能体), tool-todo ]

🧩 cordis 补丁

上述 patch 注入三个插件（主 / github-watch / feishu-watch）。面板或 Harness 改配置时，host 就地写回该文件，多数设置免重启生效（涉及 Setup 字段的保存会重启）。

💾 持久化隔离

只有 Store 开 SQLite 文件；DeepSeek Harness 提供 Session/进程环境，本系统通过窄接口(SourceHost/SessionsHost)消费，不反向依赖其内部实现。

📨 Effects / Outbox

决策后的中继/派工/投递都先存后做：入队 → 提交后执行，带合并、并发限制与指数退避重试。连续三次失败才上报系统问题。

7

Web 面板：只把"需要人"的亮出来

30 秒：面板只在"需要人"的地方出现，且直接把动作递到你手边，健康态不占空间。

在 DeepSeek Harness 网页侧边栏打开 Superagent 即可监管。面板优先展示"需要人"的活，其次是系统健康与历史。它用领域术语，内部 ID 只在折叠细节里出现。

8

技术栈：一套克制的 TypeScript 工程

30 秒：克制到只剩两个运行时依赖的 TypeScript 工程，宿主能力全来自 DeepSeek Harness。

⚙️ 语言与运行

TypeScript 6 + Node 22.19+ / 24+；包管理 pnpm 11.7。仅两个运行时依赖：proper-lockfile(文件锁) 与 zod 4(校验)。

🧱 宿主与插件

全部能力来自 @deepseek-ai/dsh-* 系列 peer 依赖（Harness、Session、Tools、LLM、权限预设、客户端 UI 等），通过 cordis 注入。

🏗️ 构建与测试

tsdown 打包、vitest 4 测试、tsc --noEmit 类型检查。pnpm check = 类型 + 测试 + 构建一次性跑完。

🖥️ 面板与存储

面板用 React 18(自绘控件，不 import 宿主 UI 原语)；持久化是单个 SQLite(orchestrator.sqlite)，由 Store 独占。

🧭 它到底解决了什么？

传统 Agent 是"问答机"；能为一个团队行动的 Agent 也可能"为一个团队制造噪音"。dsh-superagent 用一套极简领域模型 + 严格授权 + 注意力经济学，把"主动"关进笼子里：只在被要求或被规则允许时动，只在人必须行动或能用结果时才出声。它把"自动跑"和"不打扰人"这对矛盾，用工程纪律真正调和了——这正是它值得细读的地方。
