for Autonomous Model Onboarding

01 / Thesis

核心判断：瓶颈可能在环境，而不只在模型

Model Onboarding 的自动化瓶颈，不一定是 Agent 不会推理；也可能是它看不到关键工程信息、找不到可用组件，或无法操作并观察真实执行环境。
01 · VISIBILITY

知道什么、看得到什么

模型、代码、组件、约束、历史经验是否可发现、可理解，并且能判断适用范围。

02 · AGENCY

能做什么、操作得到什么

能否调用已有 API、启动任务、访问设备、读取日志、检查产物并控制执行生命周期。

03 · VERIFICATION

结果是否真的达标

由用户目标和独立验收机制判定结果；Agent 的自我判断不能替代客观验证。

工作假设，而非已证明结论：当通用模型具备足够上下文、工具权限和可靠反馈时，它可能自主规划大部分 Onboarding 步骤，不需要预先编码完整 Workflow。

02 / Scope

项目边界：建设连接层，不重造工程基础设施

底层量化、部署、测试等能力由专业团队开发；用户给出验收指标。项目重点是让 Agent 能发现、理解、调用这些能力，并在 Harness 中完成持续执行。

IN SCOPE

需要负责

上下文发现与呈现、组件目录和接口信息、源码探索能力、工具接入、远程执行、状态管理、日志反馈、任务恢复、结果汇总。

OUT OF SCOPE

不重复建设

不重新开发量化算法或设备 Runtime；不复制底层库的参数逻辑；不把每个团队组件都包装成一个 Agent；不预设唯一固定的 Onboarding 流程。

03 / Visibility

Engineering Context：让工程环境可发现、可理解

目标不是把所有信息预先塞进 Prompt，而是让 Agent 知道从哪里找、如何判断可信度，以及缺信息时如何继续探索。

DISCOVERY

1. Discoverability

问题：Agent 是否知道组件存在、归谁维护、在哪里、如何进入？

载体：组件目录、仓库索引、服务目录、API Catalog、Owner 与入口信息。

产出：可定位的候选能力，而不是一份泛化知识摘要。

UNDERSTANDING

2. Interpretability

问题：Agent 是否理解接口语义、输入输出、参数限制和调用前置条件？

载体：README、API 文档、源码、类型定义、配置 Schema、Examples、Tests。

产出：有证据支撑的调用理解。

APPLICABILITY

3. Applicability

问题：Agent 是否知道某能力何时适用、何时不适用、有哪些兼容性限制？

载体：硬件约束、模型支持矩阵、已知问题、历史案例、失败模式。

产出：能够做选择，而不只是找到 API。

Context 的信息来源与证据等级

来源最适合回答的问题可信度 / 使用方式常见盲区
Curated Skills从哪里开始、典型步骤、经验性决策、常见坑高效导航；需要标注适用范围与更新时间可能过时，不能替代真实实现
文档 / Metadata组件职责、入口、输入输出、Owner、限制适合作为快速索引和契约文档可能滞后于代码
Source Code实际行为、隐含默认值、参数逻辑、调用链实现层证据；按任务定向检索阅读成本高，代码不一定揭示运行环境限制
Tests / Examples如何正确调用、预期行为、边界条件可执行证据；优先复用已通过的用例测试覆盖范围有限
Execution Logs / Artifacts当前环境实际发生了什么任务现场证据；关联版本、配置和环境日志不完整或缺少上下文时容易误读
Historical Recipes相似模型或设备上曾经怎样成功参考证据，不应直接当成通用规则模型、工具版本、设备差异会使经验失效
原则：Skill 提供导航和经验；Metadata 提供入口和契约；源码揭示实现；Tests 与 Examples 提供行为证据；实际执行反馈验证当前环境。不要让任何单一载体承担全部知识。
04 / Context Acquisition

渐进式上下文获取，而非全量预装知识

Agent 先拿到足够的起点，再围绕当前不确定性检索。每次检索都应服务于一个明确的决策或执行需求。

→

用实际行为校验理解

Agent 应主动提出的问题

  • 我需要完成的子任务是什么？
  • 当前决策缺少哪条信息？
  • 哪个仓库、组件或接口最可能提供证据？
  • 文档与源码是否一致？
  • 是否能用低成本测试验证我的理解？
  • 当前信息是否足以安全执行下一步？

Context 获取的工程要求

  • 检索应支持仓库、符号、全文、依赖和调用关系。
  • 结果应带来源、路径、版本或提交信息。
  • 允许 Agent 从索引深入到原始源码。
  • 记录关键决策引用了哪些证据。
  • 对缺失权限、缺失文档和未知约束显式报告。
  • 控制上下文预算，避免无目的全库阅读。

建议将“Agent 自主检索”与“人工整理的导航信息”组合使用。目标不是消灭文档，而是避免人类必须提前把所有实现细节翻译成 Agent 专用知识。

05 / Agency

Execution Harness：让判断变成可控的工程动作

Harness 不替 Agent 规划每一步，而是提供稳定的执行接口、可观测状态和可靠的任务生命周期管理。

ACCESS

Tool & Environment Access

Python API、CLI、文件系统、GPU Server、设备 Farm、模型仓库、构建与部署环境。统一发现入口，保留底层工具语义。

LIFECYCLE

Execution Control

提交任务、传递配置、分配资源、查询状态、取消任务、处理超时。长任务应返回可追踪的 Job ID，而非阻塞对话。

OBSERVABILITY

Feedback & Recovery

结构化日志、错误码、指标、产物位置、运行环境与版本；支持失败分类、重试、恢复和人工介入。

Harness 必须管理的执行对象

对象建议记录的内容为什么重要
Task目标、约束、验收标准、发起者、优先级任务目标与验收标准不应散落在对话历史里
Run / Job运行 ID、Harness、Host、状态、开始结束时间、退出码区分任务意图与一次具体执行
Environment机器、GPU、驱动、依赖、容器、代码版本使结果可复现，定位环境差异
Input / Config模型版本、Recipe、参数、输入文件及校验值明确这次实验究竟运行了什么
Event / Log状态变化、关键日志、错误、工具调用摘要Agent 能理解过程，而不只是看到成功或失败
Artifact / Metric模型产物、Benchmark、精度、性能、内存、报告路径支撑验证、比较和后续交接

最小可靠执行能力

异步提交 + Job ID；状态查询；日志与产物读取；超时和取消；失败原因结构化；必要时恢复或重跑。

不要过早做的事

不要一开始就做复杂的多 Agent 状态机、通用工作流 DSL 或全面统一所有 CLI。先打通真实任务的执行、观察和恢复。

06 / Autonomous Loop

Agent 自主工作，Harness 保证任务可持续

人类定义目标与边界；Agent 决定具体步骤；Harness 管理执行事实；Verifier 判断是否达标。

Human / User Goal模型、目标设备、用户指标、约束、权限边界
↓
Agent: Plan → Discover → Decide → Act按需获取上下文；选择现有能力；制定并调整执行计划
↓
Execution Harness提交任务、管理状态、采集日志、保存产物、支持恢复
↓
Engineering Systems量化 / 部署 / 测试 / Debug / Device Farm
Independent Verifier按用户指标判定 Hard Constraints 与优化目标
↓
Evidence & Feedback成功条件、失败原因、指标、日志、产物、未解决问题
↺ Agent 基于证据决定继续、调整、补充检索或请求人工判断

人类负责

定义目标、提供用户指标、授权访问、处理高风险决策、审核最终交付。

Agent 负责

探索上下文、规划步骤、选择组件、执行操作、分析反馈、决定下一轮动作。

Harness / Verifier 负责

执行事实、状态和证据的可靠记录；按明确规则独立判定结果，不把 Agent 自评当作验收。

07 / RSI Experiment

用消融实验定位真正瓶颈

固定模型、Harness、任务难度和验收规则，逐步开放上下文与抓手。不要先比较复杂 Agent 架构，否则很难解释性能差异来自哪里。

组别提供的环境要回答的问题
A · Baseline任务说明、模型、目标设备、用户验收指标当前 Agent 在最低上下文下能做到什么？
B · Curated ContextA + Skills、文档、组件目录、关键约束人工整理的导航信息带来多少提升？
C · Autonomous DiscoveryB + 仓库检索、源码、Tests、Examples 的自主访问Agent 能否自行补齐隐含实现知识？
D · Full AgencyC + 真实工具调用、异步执行、日志与产物反馈能否从“提出方案”跨越到端到端完成？
E · RecoveryD + 状态恢复、失败重试、上下文缺口处理和跨节点交接能否可靠完成长周期、多环境任务？

实验控制变量

同一基础模型与版本；同一任务集；同一目标设备和可用资源；同一验收指标；相同执行预算。记录每次运行的代码、配置和环境版本。

失败归因标签

Context Missing / Retrieval Failure / Misinterpretation / Tool Discovery Failure / Tool Invocation Failure / Environment Failure / Planning Error / Verification Failure / Recovery Failure。

关键不是证明“加更多上下文总是更好”，而是识别哪类信息或执行能力对成功率有因果贡献，以及边际收益是否值得其维护成本。
08 / Measurement

评价指标：结果、过程、成本分开衡量

Task Success Rate独立验收通过的任务比例
First-pass Success首次完整执行即通过的比例
Human Intervention人工介入次数与介入原因
Context Gap Recovery识别并补齐信息缺口的成功比例
Execution Reliability任务状态、日志、产物完整且可恢复的比例
Cost per Success每个验收成功任务的时间、Token、GPU 与人工成本

分层诊断指标

维度指标示例解读注意
Visibility关键组件发现率、关键约束覆盖率、证据引用率、检索命中率检索次数多不代表上下文质量高；关注是否找到关键证据
Context Acquisition信息缺口识别率、缺口补齐成功率、检索耗时、无效检索比例要区分 Agent 没意识到缺信息与意识到但找不到
Agency工具调用成功率、异步任务完成率、状态可观测率、恢复成功率区分接口错误、权限问题、资源问题和工具本身失败

建议把用户指标拆为 Hard Constraints（不满足即失败）与 Optimization Objectives（满足约束后继续优化）。例如部署可运行、精度阈值、内存上限属于硬门槛；吞吐、延迟等可按用户目标进行优化。

09 / Design Decisions

关键取舍与容易踩的坑

ANTI-PATTERN

把所有知识都做成 Skill

导致重复维护、过时和上下文膨胀。Skill 应提供路径和经验，动态细节回到源码、Schema 和运行结果确认。

ANTI-PATTERN

把所有组件都封装成 Agent

组件通常是能力或服务，不需要人格化。优先提供可发现、可调用、可验证的接口，只有确有独立目标和决策空间时才拆 Agent。

ANTI-PATTERN

预先固定完整 Workflow

容易把工程师的动态探索过程硬编码。只固定安全边界、必要依赖和验收条件，把步骤选择留给 Agent。

ANTI-PATTERN

把 Agent 自评当作成功

Agent 可能误读指标、忽略 fallback 或牺牲其他目标。验收必须来自独立指标和可追溯证据。

安全与权限：Agency 不是无限制 Shell

按 Host、仓库、工具和资源配置最小权限；对破坏性操作、发布、覆盖产物和高成本 GPU 任务设置确认或配额。记录调用身份、参数和结果。不同团队组件的凭据不要通过 Prompt 传播。

上下文可信度：如何处理文档与代码冲突？

为证据附上来源、版本和时间；接口事实优先检查当前代码、Schema 与测试，运行行为以当前环境实测为准。发生冲突时向 Agent 暴露冲突，而不是静默选择一份来源。

长任务可靠性：如何避免对话断开导致任务丢失？

任务状态必须存在 Harness 的持久化记录中，而不是只存在模型上下文。恢复时重新读取 Task、Run、日志、产物和最近一次验证结果，再决定是否续跑。

跨团队组件：如何减少“人肉中转站”？

给每个组件提供 Owner、入口、输入输出、权限申请路径、SLA 或已知限制。Agent 遇到权限或接口边界时应能提出结构化请求；不要假设所有团队系统都能直接互通。

10 / Roadmap

建议实施顺序：先跑通一条真实闭环

以一个陌生模型、一种目标设备和一条现有量化链路作为试点。先证明 Agent 能端到端工作，再扩大组件覆盖。

1

选定代表性 Onboarding 任务

明确模型输入、目标设备、现有工具入口、用户验收指标和人工审批边界。记录当前工程师完成任务的真实路径，但不把它直接固化为 Agent 工作流。

2

打通最小 Context Surface

提供仓库入口、关键文档、组件目录、源码搜索、Examples / Tests，以及模型和设备约束。所有信息尽可能带版本与来源。

3

打通最小 Harness Surface

支持调用现有 Python API 或 CLI、异步提交、Job 状态查询、日志读取、产物访问和取消任务。先支持一个稳定执行环境。

4

接入独立验收

把用户指标转成机器可读的验收输入；明确硬约束、优化目标、数据来源和阈值。验证结果要与本次 Run、配置和环境绑定。

5

做消融实验并分析失败

按 A–E 逐步开放上下文和抓手；为失败标注原因；比较成功率、人工介入、耗时与成本。优先修复出现频率高且影响成功率的盲区。

6

再扩展到多 Harness、多机器和跨团队

当单链路可靠后，再引入统一任务控制面、远程 Runtime、跨 Harness handoff 和多 Agent 分工。保留各 Harness 原生能力，不为统一而统一。

11 / Summary

最终定位

不要先把工程师的工作步骤编码给 Agent；先让 Agent 获得工程师可用的信息、工具和反馈，再用真实任务验证它能否自主形成有效步骤。

项目要建设的

一个 Agent-accessible、可探索、可执行、可观测、可恢复的 Engineering Environment。

项目要证明的

在既有工程能力和用户验收标准不变的前提下，提升通用 Agent 完成新模型 Onboarding 的自主性、可靠性与单位成功成本。
